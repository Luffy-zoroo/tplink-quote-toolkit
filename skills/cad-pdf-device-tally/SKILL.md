# CAD 图纸（DWG / PDF）智能化图纸 → 设备数量统计

## ⚠️ 执行者须知（本文件是给 AI 的操作手册，不是给用户看的说明）

- **所有探测、安装、转换、统计动作都由你自己执行**，不要把"请你去装个 ODA / 请你自己转一下 DXF"
  这类话甩给用户。先自己探环境、自己跑命令，把能做的做完。
- **只有真的做不到时才降级**（例如整台机器既没有 AutoCAD 也没有任何 DWG→DXF 转换器），
  此时给用户**选择题**而不是**任务单**：要么让他把图纸另存成 DXF（一步），要么走 PDF 路线。
- **绝不猜数字**。读不到就报读不到，标注"待确认"，见文末"交付前必须标注可信度"。

## ⭐ 路线选择：矢量优先，能拿矢量就绝不走 OCR

|---|---|---|---|

**2026-09-22 实测（某城中村改造项目，约 130 行清单）：路线 A 全程约 40 次工具调用即完成逐项核对，
拿到 6476 条文字 + 1674 个图块参照，文字类数值为图纸真值。凡能拿到矢量源，不要碰 PDF OCR。**

### 路线 A：DWG 矢量直读（首选）

**工具**：AutoCAD 自带的 `accoreconsole.exe`（无 GUI 的命令行内核），位于 AutoCAD 安装目录下，
典型路径 `C:\Program Files\Autodesk\AutoCAD 20xx\accoreconsole.exe`。找不到就搜：

```cmd
where /r "C:\Program Files\Autodesk" accoreconsole.exe
```

> ⚠️ **许可提醒**：accoreconsole 是 AutoCAD 的组成部分，**不能随本技能分发**。
> 这条路要求本机已装正版 AutoCAD。**没有 AutoCAD 就改走【路线 C】（DXF + ezdxf）**，
> 那里有本技能的实测脚本，比 PDF OCR 准得多。

> ⚠️ **Git Bash 调用坑（2026-11-02 实测）**：`accoreconsole.exe /i "x.dwg" /s "y.scr"` 在 Git Bash 里
> 会被 MSYS **路径转换**成 `I:\` `S:\`，结果是只打印 Usage 什么都不干（退出码还是 0，极易误判"脚本没生效"）。
> **必须 `export MSYS_NO_PATHCONV=1`，并用 Windows 反斜杠路径。** PowerShell 下无此问题。

**调用方式**
```bash
ACCORE="C:/Program Files/Autodesk/AutoCAD 20xx/accoreconsole.exe"   # 换成你自己的安装路径
"$ACCORE" /i "图纸.dwg" /s "D:/path/extract.scr"
```

**`.scr` 内容（系统变量必须先设，否则弹框卡死或拒绝加载）**
```
(setvar "CMDECHO" 0)
(setvar "FILEDIA" 0)
(setvar "EXPERT" 5)
(setvar "SECURELOAD" 0)
(load "D:/path/extract.lsp")
ETX
```

**关键结论 / 坑**
1. **LISP 脚本只能写 ASCII 注释** —— 带中文注释的 .lsp 会加载失败，报错还不明显。
2. **`accoreconsole` 不支持 VL 函数**：`(layoutlist)` 报 `no function definition: LAYOUTLIST`。
   实测 `TILEMODE=1`，**全部实体都在模型空间**，直接 `(ssget "_X" '((0 . "TEXT,MTEXT")))` 遍历即可，不需要切布局。
3. **编码**：accoreconsole 的**日志输出是 UTF-16LE**（需 decode 后才能看）；LISP `write-line` 写出的文件是 **GBK**。
4. **图块名**取 INSERT 的 `(cdr (assoc 2 ed))` —— 这是图形符号统计的权威来源。
   /`assoc 1`=文字内容 / `assoc 10`=坐标 / `assoc 40`=字高 / `assoc 8`=图层。MTEXT 长文本会截断在 `assoc 3`，需拼接。
5. DWG 被占用会弹 MessageBox（"正在使用或只读"）—— accoreconsole 会自动应答 Yes 以只读方式打开，不影响提取。
6. 导出后**先做「图名 → 行带」定位**再统计：图签/图名文字的实测坐标 + 一维间隙分析，比全局间隙可靠
   （INSERT 块定义可能在极远坐标，如 X=-5997838，会污染全局间隙分析）。可用 PIL 把文字坐标散点渲染成 PNG 目视确认排布。

**统计口径（必须区分这两类，否则会静默得 0）**
- **A. 倍数式标注**：`名*N`、`N*名`、`含N个名` → 用 `名\s*[*×]\s*(\d+)` 求和。
- **B. 逐台点名式**：`名 300*200*120`、`42U机柜`（尺寸跟在名字后面）→ **按出现位置去重计数**。
  对 B 类误用 A 类正则会匹配不到而返回 0，看起来像"图上没有"，非常容易误判。
- **必须剔除的非设备标注**：`x1/x2/x3/x4`（户内线缆倍数）、`4*Cat.5E utp`、`RVV2*1.0`（线缆）、`n*Cat6`（线缆根数）。
- **图块 vs 文字会重复**：同一设备可能既有文字标注又有符号（如「8口楼宇交换机*1」与「联网分配器」图块），
  两者是同一台设备，**不要相加**。

**Excel 清单侧配套坑（本次踩到）**
- 清单表常有**纵向合并单元格**（如 `B12:B18` 合并成 1 项，配 `F/G/H/I/J` 列一起合并）。
  若沿用「合并单元格填充」的解析方式，会**凭空多出多行同名设备**且数量重复。
  **正确做法：用原始单元格（不做 merge 填充）+ 判断序号列是否非空**。
- 核对清单时，"计量单位"列可能整行为空（本次残卫「单防区输出扩展模块」），备注列可能是 `#NAME?` 公式错误，
  这些都要在报告里点出来。

## 路线 C：DXF + ezdxf（本机没装 AutoCAD 时）

**为什么需要这条路**：`accoreconsole` 是 AutoCAD 的组件，机器上没 AutoCAD 就没有它；
而 DWG 是闭源二进制格式，Python 侧**没有任何库能直接读**。中间必须有一次 DWG→DXF 转换。
DXF 是明文格式，`ezdxf` 能拿到和 accoreconsole 一样的实体级数据 —— **精度与路线 A 同级，不是 OCR 那种估算**。

### C-1 先探测环境（你自己跑，不要问用户）


`ezdxf` 缺失就直接装（纯 Python 包，无需编译、无需管理员权限）：

### C-3 三种转换方式（选一种，命令可直接跑）

**方式① AutoCAD `DXFOUT`（机器上有 AutoCAD 时最省事，保真度最高）**

```bash
export MSYS_NO_PATHCONV=1        # Git Bash 必加，否则 /i /s 被当成路径
mkdir -p /d/work/tmp
cat > /d/work/tmp/dxfout.scr <<'EOF'
(setvar "CMDECHO" 0)
(setvar "FILEDIA" 0)
(setvar "EXPERT" 5)
(command "_.DXFOUT" "D:/work/out.dxf" "16")
EOF
"/c/Program Files/Autodesk/AutoCAD 20xx/accoreconsole.exe" \
    /i "D:\work\in.dwg" /s "D:\work\tmp\dxfout.scr"
```
> `"16"` 是小数位精度（0~16），给 16 不会丢坐标精度。

**方式② ODA File Converter（免费，不依赖 AutoCAD，推荐给没有 AutoCAD 的机器）**

从 <https://www.opendesign.com/guestfiles/oda_file_converter> 下载安装（Windows 版约 130 MB，装完是 CLI + 极简 GUI）。
命令行一次转整个目录：

```bash
"/c/Program Files/ODA/ODAFileConverter 25.x.x/ODAFileConverter.exe" \
    "D:/work/in"  "D:/work/out"  ACAD2018  DXF  0  1  "*.dwg"
#   输入目录      输出目录        版本      格式 递归 审核  过滤
```
- 位置参数顺序固定：`<inDir> <outDir> <outVer> <outFormat> <recurse 0|1> <audit 0|1> <filter>`
- **输入/输出必须是目录，不能直接给文件**（给文件会静默不转，退出码仍是 0）
- `outVer` 建议 `ACAD2018`；给太老的版本可能丢动态块

**方式③ LibreDWG `dwg2dxf`（开源 GPL，前两条都不可用时才用）**

```bash
dwg2dxf -o out.dxf in.dwg
```
> 冷门实体、动态块匿名副本偶有丢失，**必须做 C-5 的一致性抽检**再用。

### C-4 统计（本技能自带脚本，不用现写代码）

```bash
# 概览：实体统计 + 倍数标注台数 + 块参照排名 + 文字排名 + 图层分布
python scripts/dxf_tally.py 图纸.dxf

# 导出带坐标的文字明细（复现路线 A 的「图名→行带」定位靠它）
python scripts/dxf_tally.py 图纸.dxf --csv 文字明细.csv --json 结果.json

# 按关键词找标注；按图层只统计某个系统
python scripts/dxf_tally.py 图纸.dxf --find 交换机
python scripts/dxf_tally.py 图纸.dxf --layer E-弱电

# 只看某个布局；限制排行条数
python scripts/dxf_tally.py 图纸.dxf --space paper --top 50
```

**脚本的口径（与本文档"统计口径"一节对齐）**
- `名*N` / `N*名` / `名×N` / `含N个名` → 求和，输出「设备台数」
- **自动排除**线缆类（`4*Cat.5E utp`、`RVV2*1.0`、`CAT6 x22`）和尺寸/坐标类（`600x600 地砖`、`@300*150`）
- 块参照按**块名**计数；`TO ×24` 这类点位符号也会被倍数解析捕获，可直接用于点位类型统计
- **默认扫全部空间**（模型 + 所有布局），和 `accoreconsole` 的 `ssget "_X"` 口径一致

**读不出来时会明确报错并给下一步**（不会静默返回 0）：喂 `.dwg` 退出码 3 + 三条转换路径；
一个字都没读到 → stderr 提示"可能文字被炸成曲线 / 图层被过滤 / 内容在块里未实例化"。

### C-5 与路线 A 的一致性（2026-11-02 实测，可复现）

同一份 DWG（4.2 MB）现场 `DXFOUT` 成 27 MB DXF，两条路线逐实体对比：

| 口径 | 路线 A（`accoreconsole` + LISP `ssget "_X"`） | 路线 C（`ezdxf`） |
|---|---|---|
| 文字实体（TEXT+MTEXT） | **1022** | **1022**（TEXT 1008 + MTEXT 14） |
| 块参照 | **2720** | **2720** |
| 块名直方图（逐个块名比次数） | — | **差异 0 条** |

**结论：只要转换器不丢实体，路线 C 的读数和路线 A 完全一样，可以当权威值用。**

⚠️ 但一个反例必须记住：同一份 DWG 的**另一份旧转换件**（27 MB，`site2013.dxf`）读出来是
**1006 / 2713**，差 1.5%。查下来不是转换丢东西，而是**那份 DXF 是另一个版本的图纸**。
→ **拿到别人给的 DXF，先核一句"这是不是当前版"，再当现行版用**；能从 DWG 现场转就别用旧转换件。

### C-6 这条路的坑

1. **布局里有内容，只扫模型空间会漏。** 本例「布局1」里还有 7 个块 + 10 条文字（多半是图签/设备表）。
   `accoreconsole` 的 `ssget "_X"` 是全库，所以脚本默认 `--space all`；你写成 `--space model` 就会少几百上千条。
2. **编码**：R2018 及以上 DXF 是 UTF-8；老版本走 `$DWGCODEPAGE`（本例 `gbk`）。
   脚本第一行会打印实际编码 —— **中文乱码先看这一行**，别急着怀疑图纸。
3. **匿名块名不能当设备名**：`A$C24FE3AAA`、`*U465`、`$DorLib2D$00000002`、`$TwtSys$00000545`
   是天正 / 第三方插件的动态块派生副本，同一台设备会换着名字出现。**只认有中文或明确英文名的块**。
4. **DXF 体积通常是 DWG 的 5~7 倍**（4.2 MB → 27 MB），读一次约 7 秒。别用 DXF 做归档，只做中间产物。
5. **倍数解析会撞上尺寸写法**：`@300*150` 是相对坐标、`600x600 地砖` 是尺寸，都不是台数。
   脚本已按「设备名必须含字母或汉字」+「`x` 两侧有数字则判为尺寸」两道闸滤掉，
   **但报告里仍要抽查**：出现"合计 150 台某某"这种明显不对的数字，回去 `--find` 看原文。
6. **`ODAFileConverter` 给文件路径不报错、也不转。** 它的输入输出都是**目录**，只转目录里匹配 filter 的文件。

## 关键陷阱

0. **⭐ 最重要的一条：读小字数量格必须用「2400 dpi + 局部裁剪」，不要用低 DPI 整页渲染。**
   整页 600 dpi 渲染时，CAD 的细笔画被抗锯齿稀释到阈值以下，会产出大量**「假空白」**格子 ——
   实测同一格（第 5 页 6F·24 口配线架）600 dpi 只有 **6** 个墨迹像素，2400 dpi 局部裁剪下有 **152** 个，
   于是"有数字"被读成"没标注"，整张表全错。
   关键点：`dpi` 高会触发 MuPDF 的 `Overly large image` 限制，**所以必须先 `clip` 到很小的区域再提高 dpi**。
   `Rect` 很小 + `dpi=2400` 可以正常渲染；整页 `dpi=900` 才会失败。
   ```python
   pm = doc[pno].get_pixmap(dpi=2400, clip=pymupdf.Rect(xa, y0, xb, y1),
                            colorspace=pymupdf.csRGB, alpha=False)
   ```
1. **★ 先做一件事：试一次 `Read` 一张 PNG。** 如果成功返回图像，**这是本任务最高效的手段，全程首选「局部裁剪 → 高 dpi 渲染 → 直接 Read PNG」**，比 OCR 和点阵字符画都快且准。**该能力在部分环境不可用**（会返回 `model does not support images`），此时才退回到 **OCR 结果 + 像素哈希/差分 + 点阵字符画**。（本技能旧版把"读不了 PNG"写成硬结论，导致多绕了很多弯路 —— 每换一个环境都要重新试一次，不要照搬。）
2. **OCR 会把 CAD 细笔画漏掉** —— 渲染前必须做「墨迹提取 + 对比度拉伸」，见下面 `render_ink`。
3. **数字识别（0/6/8/9）在细笔画下不可靠** —— 数量列务必用「同格像素比对」确认，不要只信 OCR。
4. **图纸会有标注缺漏**（数量栏空白）—— 只统计明示值，并在报告里显式列出空白楼层，不要脑补。
5. **不要把"每层一台"这类工程直觉当成读图结果。** 用户对这一点极其敏感，会直接质疑"你根本没看图"。

## 步骤 1：确认矢量 & 定位系统图页

```python
import pymupdf
doc = pymupdf.open(pdf)
for pno in range(len(doc)):
    t = doc[pno].get_text().strip()
    d = doc[pno].get_drawings()
    print(pno+1, len(t), len(d))   # 文本≈0 且 drawings 很多 → 纯矢量
```
页码↔系统靠 **OCR 图纸内标题栏 / 左侧图签**确定，不要靠页码序号猜。

## 步骤 2：墨迹提取渲染（核心）

CAD 线条很细、颜色很浅，直接光栅化 OCR 会大面积漏检。

```python
import numpy as np, pymupdf
from PIL import Image

def render_ink(page, dpi=400):
    pm = page.get_pixmap(dpi=int(dpi), colorspace=pymupdf.csRGB, alpha=False)
    a = np.frombuffer(pm.samples, np.uint8).reshape(pm.height, pm.width, 3)
    ink = (255 - a).max(axis=2).astype(np.float32)      # 取最深的通道作为"墨"
    p = np.percentile(ink, 99.5)
    gain = 255.0 / max(p, 1e-6)                          # 自适应拉伸
    out = np.clip(ink * gain, 0, 255).astype(np.uint8)
    return Image.fromarray(255 - out)                    # 黑字白底
```
缩放关系：`px = pt * dpi / 72`，OCR 得到的像素框要按此换算回 PDF 坐标（pt），便于跨页对齐。

## 步骤 3：分块 OCR（整页 OCR 会漏）

整页喂给 OCR 时，字号小的表格常被吞掉。用带重叠的分块 + IoU 去重：

```python
def scan_page(doc, pno, dpi=400, nx=4, ny=3):
    img = render_ink(doc[pno], dpi)
    W, H = img.size
    res, boxes = [], []
    for iy in range(ny):
        for ix in range(nx):
            x0 = int(W*ix/nx*0.92); x1 = min(W, x0 + int(W/nx*1.16))
            y0 = int(H*iy/ny*0.92); y1 = min(H, y0 + int(H/ny*1.16))
            sub = img.crop((x0, y0, x1, y1))
            for r in ocr(np.array(sub)):
                # r = [box, text, score]
                pts = [(x0+p[0], y0+p[1]) for p in r[0]]
                if any(iou(pts, b) > 0.5 for b in boxes): continue
                boxes.append(pts)
                res.append({"text": r[1], "score": r[2],
                            "pt": [[x*72/dpi, y*72/dpi] for x, y in pts]})
    return res
```
OCR 打印时坐标要转 str：`print([str(x) for x in r[1]], r[2])`，否则 `round()` 会对 str 报 TypeError。

**已知识别偏差**：细笔画下 `0/6/8/9`、`1/7`、**`3/8`** 易混；带下划线的字易被拆成两段。

### 步骤 3.5：像素点阵复读（Read 读不了 PNG 时的替代手段）

单看 OCR 文本一定会错（实测：把 `8` 读成 `3`）。当某个数字存疑时，把它还原成**点阵字符画**，直接"用眼睛读"。（**优先试 Read PNG；只有在 Read 不支持图像的环境里，字符画才是唯一能真正看图的办法**）：

```python
def art(ink, S, x0, y0, x1, y1, cols=64, rows=18):
    g = (ink[int(y0*S):int(y1*S), int(x0*S):int(x1*S)] > 110).astype(np.uint8)
    h, w = g.shape
    for i in range(rows):
        row = ''
        for j in range(cols):
            blk = g[int(i*h/rows):max(int((i+1)*h/rows), int(i*h/rows)+1),
                    int(j*w/cols):max(int((j+1)*w/cols), int(j*w/cols)+1)]
            row += '#' if blk.mean() > 0.34 else ('+' if blk.mean() > 0.12 else '.')
        print('  ' + row)
```
- 单字符宽度：CAD 字体很窄，约 `2.2 pt/字`，裁剪窗口别超 3 pt 否则会带出下一个字。
- **判别数字不能只看宽高比**。本类图纸 5 个数字的宽高比高度重叠，必须看**竖笔落在哪一侧**：
  | 数字 | 宽高比 | 一眼判据 |
  |---|---|---|
  | `1` | 0.18–0.19 | 一根长竖笔 + 顶部向左上一小撇，无横梁 |
  | `2` | 0.36–0.37 | 顶圆弧 → 右竖下行 → **中部一段长斜线直插左下** → 底部满横 |
  | `3` | 0.35–0.36 | 顶横 + 右竖；**中部是朝左的尖（V 形缺）**，上下两半竖笔都在右侧 |
  | `5` | 0.36 | 顶横 + **上半段竖笔在左侧**，中部横梁，**下半段竖笔在右侧**，底部横 |
  | `4` | 0.45 | 左斜笔 + 中部横梁 + **右侧一根贯穿横梁上下的竖笔** |
- **`3` vs `5` 是最频繁的误读点**（两者宽高比≈0.35/0.36）：看上半段竖笔在**右**还是**左**。
- **`3/8` 旧经验不适用于此字体**：本类 CAD 字体的 `3` 左右两侧都有笔画，别再套"只有右侧笔画"的判据。
- 2400 dpi 局部渲染下可直接辨认，无需拉伸放大。

### 步骤 3.7：表格数量栏 —— 最容易翻车的地方（血泪教训）

小字号数量格（单字宽约 **2 pt**、高约 **6.5 pt**）是整张图最难读的部分，**统计数字最后出错，几乎都出在这里**。

**必须避开的坑：**
1. **低 DPI 整页渲染会产出"假空白"（最致命的坑）**。600 dpi 整页渲染时细笔画被抗锯齿稀释，格子里明明有数字却量不到墨迹，看起来像"图纸没标数量"。
   **正解：只裁「数量」列的小区域，再上 2400 dpi。** 局部 clip 不会触发 `Overly large image`。
   （整页 `dpi=900` 确实会报 `MuPDF error: limit error: Overly large image` 并返回全黑数组 —— 这是"整页高 DPI"的问题，不是"高 DPI"的问题，别因此退回低 DPI。）
2. **框线会污染计数**。行区间若没避开上下横线，量到的"墨迹"其实是框线像素，会凭空出现 67/73/74 这类整齐的假值。行区间改用「检测到的表格线」定位，并把格子**内缩 0.6 pt** 再取墨迹。
3. **RapidOCR 检不出这种小字**（检测阶段直接失败），裁剪后放大 3～4 倍也没用。别在这上面浪费时间。OCR 只用来定位"数量"列的 x 坐标和楼层标签，**不要用它读数字**。
4. **不要用固定偏移量定位行**，块与块之间会累积漂移。用检测到的表格线逐块对齐，并用块间距（PITCH）推算块顶。

**推荐流程（可复现，已在真实项目跑通）：**
```
① OCR 结果（坐标）→ 定位每页「数量」列的精确 x 区间（各页往往不同，必须逐页量）
② 只裁该列竖向长条 → 2400 dpi 局部渲染 → 二值墨迹图
③ 横向墨迹投影找表格线（占列宽 ≥60~70% 才算线）→ 块顶对齐到最近的线 → 块内按行距取 3 个设备行
④ 每格裁到墨迹外框，**保持宽高比**（只按高度归一，宽度同比缩放后居中）
⑤ 同页同字号的字形做位图互比聚类（Jaccard 距离 < 0.30）→ 每类打印原生点阵画，人工定字 → 回填
⑥ 用「分项之和 = 合计」+「与配单/清单对照」做整页校验
```
**绝不要做「宽度拉伸到固定 W」的归一化** —— 那会把 `1/4/5` 挤成同一个形状，聚类直接合并，是另一处独立的错误来源。只归一高度、保留宽度比例。

**判定空白的阈值（含 dpi，不要跨 dpi 套用）**：
- 2400 dpi 局部裁剪：真实数字 ink ≥ 60；`1` 约 100～270，`2` 约 140～270，`3/4/5` 约 150～290；ink < 60 视为空白。
- 600 dpi 整页：**不可用**，会出现 ink=0～6 的假空白。
- 反过来，若某格 ink 异常大且外框特别宽，先怀疑把框线或邻格吃进来了。

### 步骤 3.8：跨页/跨层「同配置」结论必须逐格验证

系统图各页常出现外观相同的「弱电间设备表」。**绝不能因为表头和行标签一样就推断每层数量相同**。

正确做法：把每层的数量列（3 行）做**像素哈希**，按签名分组：
```python
sig = tuple('空' if (cell>35).sum()<25 else md5(packbits(cell)).hexdigest()[:6] for cell in three_cells)
```
- 若 N 层得到 N 种签名 → **每层都不一样**，必须逐层读。
- 若确实聚成少数几类 → 才能说"典型配置"，且要注明是哪几层。

实测教训：曾据"表头相同"推断 4 个系统、16 层都是「1 台 24 口 POE + 1 台 48 口 POE」，逐格验证后发现**每层配置互不相同**，结论全部作废。

**从像素哈希还能读出"设计是怎么画的"**（实测有效）：
- 若若干页该表 **逐格哈希全部相同** → 是**整块复制**的，那么"各系统台数不同"的物理合理性就不成立，多半是设计图省事。
- 若某页在某些层上与其他页不同 → 说明**本意是按系统分别编制**，而不是"弱电间共用表"。
- 这两种情况同时出现时（如 P7≡P8≡P9 但 P6 有三层不同），说明图纸本身自相矛盾，**必须把"共用 / 各自独立"两种口径分别算出结果并请设计确认**，不要替设计选一个。

### 步骤 3.10：表格完整性核对（防止漏掉楼层块）

统计前先数一遍**表格块数**，别假设"楼层数 = 块数"：
- 用横向墨迹投影检测每列的所有表格线，块顶应呈**等间距**（PITCH，如 114.26 pt）。
- 检查每个槽位是否真有线：**整块空白 = 该层没有弱电间**（本项目 18 层楼里 4F、14F 无弱电间，楼层序列跳号）。
- 用 OCR 的楼层标签坐标反证跳的是哪一层，**不要凭常识猜**。
- 最终核对：`列数×每列块数×每块行数 == 逐格产物条目数`（本项目 3 列共 16 层 × 3 行 × 5 页 = 240 格）。

### 步骤 3.9：交付前必须标注可信度

数量表这类密集小字内容，**在交付物顶部显式写出"哪些已逐格复核、哪些是推断"**。宁可标"待确认"，也不要把推断当数据交付。

### 步骤 3.6：分项之和 = 线缆总对数（最强的交叉校验）

系统图通常同时标了「分项设备数」和「同层线缆总对数」，例如：

```
2×(CAT6-UTP-CT-PVC20)/吊装无线     ← 吊装 AP 2 个
20×(CAT6-UTP-CT-PVC20)/面板无线    ← 面板 AP 20 个
CAT6 x22                            ← 该层 CAT6 共 22 对
```
**分项之和必须等于总对数**。不等就说明某个数字读错了 —— 实测靠这条抓出了 `17F 面板 8 被误读成 3`（12+8=20 ✓，12+3=15 ✗ 对不上 CAT6 x20）。

逐层把三者列出来对一遍，比逐格盯 OCR 可靠得多。

### 步骤 3.6.5：⭐⭐ 系统图右侧的「极小符号列」＝ 点位类型的唯一数据源

**这是本技能最重要的一条补充，曾因漏看它而给出错误结论（"系统图只有用途汇总、没有符号类型，要数 TD/TO 得逐张读 60 张平面图"）。**

系统图每层标注行长这样：

```
[24×(CAT6-UTP-CT-PVC20)/有线网络]        [TO   ×24]
 ↑ 主标注区（≈2.2 pt/字，OCR 可读）        ↑ 符号列（≈1.3 pt/字，OCR 读不出）
```

- **主标注区**给的是「线缆对数 + 用途中文描述」；
- **紧贴右侧**还有一个**独立的极小符号列**，给的是「**点位符号 + 数量**」（如 `TO ×24`、`TO/TP ×30`、`TP ×3`、`AP ×2`、`TAP ×20`），**字数约为主标注的一半**。

**为什么容易漏**：这一列字太小（1.3 pt），在一整页缩略图里几乎不可见；且它和主标注不在同一个 OCR 能识别的块里。

**怎么读**：
```python
# 1) 先从主标注的 OCR 结果拿到每层区块的 y 范围与符号列的 x 范围
#    （符号列 x ≈ 主标注区左边界 + 一个偏移，需在页面上量一次）
# 2) 只裁这一列、逐层裁片，纵向拼成一张高图（montage），一次 Read 读完所有楼层
# 3) dpi 取 900–2400（1.3 pt 的字，低于 900 会糊）
```
- ⚠️ **RapidOCR 对这一列完全无效**（太小，只返回个位数条目）→ 必须 **Read PNG 直读**；若环境不支持读图，只能对每个符号单独做 2400 dpi 点阵字符画逐字辨形。
- 符号与图例（设计说明页）对形：**椭圆 = 外网/吸顶，方框 = 面板，双线椭圆 = 双口点位，半圆 = 摄像机**。判 `TO` 还是 `TD` 只能靠逐像素比形，**不要凭 OCR 猜字母**。

**⭐ 权威性规则（务必记牢）**：**符号列的数量是权威值，主标注正文的数字可能是笔误。**
冲突时一律以符号列为准。实测两处：
| 层/页 | 主标注正文 | 右侧符号数量 | 判据 |
|---|---|---|---|
| P5 的 2F · IP电话 | `11×` | `x0` | 53+0=53 = 同层 CAT6 x53 ✓（若用 11 则不闭合） |
| P6 的 17F · 面板无线 | `3×` | `x8` | 12+8=20 = 同层 CAT6 x20 ✓（若用 3 则不闭合） |

**⚠️ 但反过来不成立：不闭合 ≠ 一定笔误。** 必须**先用高 dpi 目视确认正文数字与符号数字是否一致**，再判断：
- 若两者**不同** → 是笔误，以符号列为准；
- 若两者**相同但与 CAT6 对不上** → 是**图纸真实的量差**，应作为"待设计确认"报出去，**不要自己编一个数字去凑闭合**。
实测案例：P6 的 **2F**，吊装无线正文与符号列**都写 14**，同层 CAT6 却标 **x15**，且该层整块**只有一行标注、没有面板无线行**（2000 dpi 放大确认"CAT6 x15"与"14×"无误）→ 真实差 1 对。同一张图上，18F 的面板无线 1× **不属于** 2F，容易张冠李戴。

**推广**：任何一层"分项之和不等于总对数"，先怀疑**主标注正文有笔误**，去核对右侧符号列；**两者一致时**才升级为图纸量差。本项目按此规则重读后，P5 的 **16 层 100% 闭合**（总对数由 788 修正为 777），P6 仅 2F 一处真实差 1 对。

**顺带产物**：读符号列还能读出「哪些图例符号其实没被使用」。本项目 P5 只出现 `TO/TP/TV` 三种，而图例定义的 `TD/2TD/2TO/TDP/2LC/APW` 六个符号 **16 层里一次都没出现** —— 这是可提交设计的实质疑问，属于高价值副产品，务必在报告里单列。

### 步骤 3.6.6：把「行/列」对上「楼层号」（否则数据无法使用）

系统图常把多个楼层的区块**排成若干行 × 若干列**（本项目为 8 行 × 3 列 = 16 个弱电间，行距 PITCH≈114.26 pt）。**同一行里 L/M/R 三列是三个不同楼层**，不是同一层的三部分 —— 认错就全盘错。

可行做法：
1. 用 OCR（整页 OCR，**不是**小块窗口）扫所有形如 `(NF-RD)` 的房间标签，拿到它们的 x/y 中心；按 x 聚成几簇（= 列），按 y 聚成几簇（= 行）。本项目标签 x 簇 ≈ 722 / 1066 / 1411。
2. 把每个区块的「分项之和」或「CAT6 总对数」与已知的逐层数据表（如综合布线页）**逐层反证**：本项目无线页 16 层的 CAT6 对数与综合布线页的逐层对数**逐层吻合**，才敢确认映射正确。
3. 映射结果写进报告/记忆，后续复用。

### 步骤 3.6.7：读一层全部标注行时，别只用一个 x 窗口

标注文字长度不一，固定窗口会**漏掉某一行**（且漏掉时不会报错，只会让该层"不闭合"）。本项目 OCR 窗口 `L_ann` 就漏掉了 8F/7F 的「24×/有线网络」行，导致误判"这两层不闭合"。
- 对策：窗口取宽一点、或用两个重叠窗口；**并始终用"分项之和 = CAT6 总对数"兜底**——不闭合就去把该层整块渲染出来逐行目视。

## 步骤 4：表格「逐格」读取

系统图里的设备表是固定网表结构，先定位**行基线**和**分组列起点**，再逐格裁剪：

```python
ROW_Y = [...]        # 每行 y（pt），从 OCR 出来的楼层标签逐行求和得到
GRP   = [...]        # 每组列的 x 起点
```
- **先做一张逐层拼图（montage）**：把每一层的同一张表裁出来，拼成一张带楼层标签的大图，一次 OCR 全读，比逐格调用快且可比对。
- **跨页比对**：对同一格的像素做哈希（或直接 `ImageChops.difference` 后统计非零像素），判断「不同页的同一张表是否完全相同」。这是发现"设计采用典型画法、四个系统共用同一张弱电间表"的关键手段。

## 步骤 5：交叉验证（必做）

1. **加总校验**：把图上散落的 `CAT6 xN` / `N×(线缆型号)` 总数与表格 AP/摄像机数相加核对，能发现漏读。
2. **与材料清单对账**：同目录的 `*设备材料清单*.xlsx` 通常存在。若清单数量（取整、预设）与图纸逐层统计**不一致**，报告里必须点明，并提示"清单疑为投标预设清单，以图纸为准"。
3. **空白格**：数量栏为空的楼层要单独列出，标为"图纸标注缺漏，需设计确认"。

## 步骤 6：交付

单文件 HTML 报告（自包含、双击即开，符合该用户偏好），分节：
1. 页码 ↔ 系统对照表
2. 各系统逐层设备表
3. **交换机按系统分开统计**（用户高频需求：网络要分**信息网** vs **设备网**）
   - **信息网** = 电视(IPTV) + 有线上网 + AP(无线上网)
   - **设备网** = 监控 + 门禁 + **广播**
   - ⚠️ **归属口径是客户/项目级的商务约定，会变**（本项目就曾先定"广播归信息网"、后改为"广播归设备网"）→ **每次开工前向用户复述一遍口径并确认**，不要照搬上一轮结论。口径一变，"缺口落在那张配单上"的结论会整体翻转，但设备总数不变。
   - 广播**只统计交换机**，功放/音柱/音箱等前端设备不在清单范围内（别当成漏项）。
   - 核心层单独列（万兆核心交换机常为 1 信息网 + 1 设备网）。

3.5 **⭐ 必问：同一个弱电间的多个系统，是"各系统各配一批交换机"还是"共用一批"？**（本项目实测为**共用**）
   - 这两种口径下的台数能差好几倍（本项目 PoE 交换机 16 台 vs 64 台），且直接决定配单该不该加设备。**绝不能自行假定，必须问用户实际工程做法。**
   - **判据一（图像）**：如果若干系统图的设备表**逐像素完全相同**、另有某一系统**不同** → 相同的那些是**共用同一批设备**的正常表达，不同的那个是独立配置。本项目即 P7≡P8≡P9（监控/门禁/广播共用）、P6（无线）不同。
   - **判据二（容量）**：算 `交换机端口数 vs 前端设备台数`。本项目设备网共用一套 = 456 口，容纳监控 223 + 门禁 49 = 272 台（占 60%），余 184 口给广播 → 合理；若各配一套则 1368 口，利用率不足 20% → 明显不合理。**前端"接得下"就是共用成立的最直观证据。**
   - **判据三（配线架反算）**：`交换机端口合计 ÷ 24` 应等于配线架台数，能整除并吻合才说明口径自洽。本项目信息网 1440÷24=60、设备网 456÷24=19，**两组都整数吻合**，是口径正确的硬验证。**这条要写进报告。**
   - 计总量时，共用设备**只计一次**，并在报告表格里显式标注"（共用，不重复计）"，否则读者会把相同的几页再加一遍。
4. KPI 卡片
5. **口径与可信度说明**（共用 vs 独立、空白格、未纳入项）

## 已踩过的具体坑
- **⭐ 600 dpi 整页渲染 → 大量"假空白"格子**（同一格 600dpi=6 px vs 2400dpi 局部=152 px）。**只裁「数量」列 + 2400 dpi**。
- **`get_pixmap(dpi=900)` 整页会静默失败**：报 `limit error: Overly large image`，返回全黑数组。但 **`dpi=2400` + 小 `clip` 是正常可用的**，别因为整页的报错就退回低 DPI。
- **把字形"拉伸到固定宽度"做归一化 → 1/4/5 合并成同一类**，聚类结果全错。只归一高度、保留宽度比例。
- **只靠宽高比区分 2/3/5 → 必错**（三者都是 0.35～0.37）。必须看竖笔在左还是在右。
- `get_pixmap(dpi=float)` → 必须 int。
- 内置 env 无 fitz → 自建 venv，用 `import pymupdf`。
- **Read 是否能读 PNG 因环境而异 → 每换环境先试一次**。可用则「裁剪 + 高 dpi 渲染 + Read PNG」为首选；不可用（`model does not support images`）才退回 OCR + 点阵字符画 + 像素比对。**不要照搬旧结论。**
- 行区间没避开框线 → 量到框线像素，凭空得到 67/73/74 这类整齐假值。
- 用固定偏移量定位行 → 块间累积漂移，同一张图不同楼层结果自相矛盾。
- RapidOCR 对小字号数量格完全无效（检测阶段失败）。仅用于定位"数量"列 x 区间与楼层标签。
- montage 表行 y 坐标必须从框线或楼层标签反推，硬编码会错行。
- **据"表头相同"或"工程常理"推断各层数量相同 → 结论全错**。必须逐格像素哈希验证。
- **⭐ RapidOCR 对长宽比极端的图直接返回 `None`（不是空列表，是 None，且不报错）**：把整层区块裁成 1160×114 pt 的长条渲染后 OCR → 0 条结果。同区域切成 250pt 宽的小块后正常识别。**判断阈值：宽度 > ~5000px 且 宽:高 > ~8 时基本必失败**。→ **宁可多切几块，也不要渲染长条**。
- **DPI 不是越高越好**：同一小块文字，700 dpi 识别正常，2000 dpi 反而识别失败（笔画被放大成灰阶、边缘模糊，字形失真）。**本项目最佳区间是 600–900 dpi**；只有读 1–2 个字符的极小数字格才需要 2400 dpi。**先试 700，不行再往上加**。
- **点位统计要先确认"系统图有没有符号类型列"再下结论**：本项目 P14（首层综合布线平面图）300 dpi 全页 OCR 只识别出房间名与尺寸，**没有任何位号文字** —— 平面图上的点位是纯图形符号，**平面图确实无法 OCR 统计**。**但系统图的每层标注行右侧紧贴一个极小符号列，含完整的「点位符号 × 数量」**（见步骤 3.6.5），这才是点位类型统计的正确数据源。**开工前先确认哪些页是系统图、哪些是平面图**（扫每页右下角图名栏最快：裁 `x∈[1470,1683], y∈[900,1010]` + 700 dpi OCR，73 页约 2 分钟）。
- **逐层标注的通用校验**：系统图上每层会同时标「分项用途点数」与「同层线缆总对数」，二者必须相等。**用这条闭合关系就能自动筛出读错的格子**。★ 实测本项目的"不闭合"**全部是主标注正文笔误**（2F、17F），去核对右侧符号列后 16 层 100% 闭合。**所以不闭合时的正确动作是「回头看符号列」，不是「再重读一遍主标注」。**
- **自己上一版报告里的"勘误清单"也可能是被假空白误导后写出来的**，重做时要连同勘误一起推翻重验，不要在其基础上修补。
- **单页读数的可信度要靠"与外部清单的独立吻合"来自证**：本项目读到 P5 的 24 口非 PoE=6、48 口非 PoE=19、P6 的 24 口 PoE=16，三处与配单**零误差吻合**，才敢对外交付。写报告时把这三处校验明确列出来。
- **⭐⭐ 大坑：把"多页设备表逐像素完全相同"一律判为"设计员复制偷懒/图纸错误"，并据此推出"各系统应各配一批"** —— 本项目在此栽了整整四版。**同一现象有两种截然相反的含义**：
  - **①共用表达（本项目的真相）**：这几个系统共用同一批弱电间设备，设计院在每个系统图上都放同一张表（都从同一弱电间取电取网）。**这是正常且规范的做法**，配单只配一套才对。
  - **②复制偷懒（需确认）**：确实画错/漏画，需要设计补充各自的配置。
  - **分辨方法**：先看**有没有哪一页不一样**（有 = 各系统独立编制，全同 = 大概率共用）；再用**端口容量**和**配线架反算**验证哪种口径自洽；最后**问用户实际工程做法**。不要只凭"工程常理说不通"就自行判为错误 —— 本项目正是凭"监控/门禁/广播不可能逐层台数相同"这个"常理"判成错误，方向完全反了。
- **读到的数字与配单不一致时，先分清是"图纸少标""口径不同"还是"配单少报"**。**在口径未确认前，不要急着报"缺 XX 台"** —— 本项目前几版报的"缺广播一套""缺门禁一套""配线架多 1 台"全部是口径判断失误造成的**假缺口**，口径确认后两张配单 13 项逐项全吻合、一台不改。**把口径确认排在缺口结论之前。**
- **报"配单多配/少配"之前先做端口反算**：`交换机端口合计 ÷ 24 = 应有配线架台数`。本项目信息网 1440÷24=60，与配单完全一致 —— 而按图纸表格直接相加只得 59，差点误报"多 1 台"。
- **Git Bash 里跑 `accoreconsole` 必须 `export MSYS_NO_PATHCONV=1`**：否则 `/i` `/s` 被 MSYS 转成 `I:\` `S:\`，程序只打印 Usage、**退出码还是 0**，看起来"跑了但没效果"。改用 PowerShell 或加这个环境变量，路径给 Windows 反斜杠。
- **只数模型空间会漏布局里的图签/设备表**：本例「布局1」还有 7 个块 + 10 条文字（占总块数 0.26%）。`ssget "_X"` 是全库口径，`dxf_tally.py` 因此默认 `--space all`。
- **拿到别人给的 DXF，先确认它是不是当前版图纸**：同一份 DWG 的旧转换件读出 1006/2713，现场重转后是 1022/2720，差 1.5% 全是版本差、不是转换丢实体。**能用 DWG 现场转就别用旧 DXF。**
- **`ODAFileConverter` 的输入输出都是目录**：传文件路径它不报错也不转（退出码 0），会让人以为"转完了"。
- **倍数解析会撞尺寸写法**：`@300*150`（相对坐标）、`600x600 地砖`（尺寸）不是台数，`dxf_tally.py` 已按"设备名必须含字母或汉字"+"`x` 两侧有数字视为尺寸"过滤；但报告里出现可疑大数时要 `--find` 看原文，别直接交付。
