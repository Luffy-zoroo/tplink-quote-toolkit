## 这个技能解决什么

用户（TP-LINK 南昌办售前）经常收到甲方给的**弱电智能化工程清单**（Excel），清单里只有项目名称和型号（TL- 开头），需要他逐行补齐两件事：

1. **参数列** —— 填控标参数（投标控标用）。优先用本地控标库（带 ★ 加分项）；库里没有的型号，去官网抓「产品特性」**+「规格参数」能力项**（带机量/转发性能…），统一成分条编号。
2. **含税单价列** —— 按型号去 CRM 查标准价，乘折扣率算出对外报价。

还要守两条硬规矩：
- **参数不得出现品牌性字眼**（否则等于指定品牌，容易被认定排他）。
- **对外报价不出现折扣明细、且不留零头**。

## 📦 第一次用：先装「数据包」（数据文件不在仓库里）

**本仓库只含代码与文档，不含数据。** 控标库 / 选型库 / 价格备份 / License 映射 / 防火墙规格都是公司内部数据，
单独打成一个 **`TP-LINK清单工作流-数据包-<日期>.zip`** 放在**内部共享盘**（公开仓库故意不放）。

**装法三步**（包内的 `00-先读我.md` 有更详细的图文步骤）：

```bash
# ① 装技能
git clone https://github.com/Luffy-zoroo/tplink-quote-toolkit.git
cd tplink-quote-toolkit && pip install openpyxl && python install.py

# ② 把配置里的数据路径指向数据包（旧配置自动备份，加 --dry-run 可先看会改什么）
python <数据包目录>/生成配置.py

# ③ 编辑 %USERPROFILE%\.workbuddy\tplink-toolkit.config.json
#    填 crm_base / dealer_base / crm 账号 / dealer 账号（域名和账号找同事要，包内不含凭据）
#    然后重启 WorkBuddy（技能是启动时加载的）
```

**包内文件名 ↔ 程序里的原名**（程序按**配置里的路径**找文件，两边的文件名必须对得上）：

| 包内文件 | 程序原名 | 少了会怎样 |
|---|---|---|
| `数据/1-控标参数库.json` | `tplink_kongbiao_data.json` | 参数全落官网兜底，**拿不到 ★ 加分项** |
| `数据/2-选型库.json` | `tplink_dealer_backup.json` | **选型直接做不了**（候选型号几乎全靠它反查） |
| `数据/3-价格备份.json` | `tplink_crm_price_backup.json` | 只能联网查价，CRM 不通就没价格 |
| `数据/4-License映射.json` | `tplink_license_map.json` | 防火墙多合一库的 SKU 取不到 |
| `数据/5-防火墙规格.json` | `tplink_fw_spec_20251120.json` | 防火墙带机量/吞吐无本地兜底 |
| `周报/项目背景.md` | — | 周报技能没有登记表（空白模板，自己往里写） |

> 文件名前加 `1-`~`5-` 只是为了好认，**程序不看名字看配置**；改过名重跑一次 `生成配置.py` 即可。
> ⚠️ 数据包**别外传、别上传到任何公开位置**。换电脑或挪了文件夹位置，也是重跑 `生成配置.py`，不用手改路径。

> **给 AI 的判断**：用户第一次上手，或报「找不到控标库 / 没有候选型号 / 参数全是官网兜底」时，
> **先让他跑 `python 自检.py`**（仓库根目录，30 秒），别一上来就改代码。
> 自检会直接说清是哪一层坏了：
>
> | 自检输出 | 真实原因 | 怎么修 |
> |---|---|---|
> | `控标库路径已配置，但文件不存在` | 配置指向的位置没文件 | 重跑 `生成配置.py`，或把 json 拷到该位置 |
> | `[选型库] 读到 0 条` | 选型库路径错 / 没装 / 从没备份过 | 同上；纯没备份过则跑 `backup.py refresh` |
> | `FATAL 没装 openpyxl` | 依赖没装 | `pip install openpyxl` |
> | `FATAL tpkit_config.py 副本不同步` | 改了源文件没同步副本 | 按 README「目录结构」那五条 `cp` |
>
> **2026-10-19 实测**：早先这两处都是「静默降级」——路径配错时只输出 `命中 0 条` /
> `（未加载，将全走官网）`，用户会误以为「库里没这个产品」，实际是路径写错。现在已改为显式报错。

**之后怎么更新**（同事最常问的一条）：

| 更新什么 | 怎么做 | 生效方式 |
|---|---|---|
| 技能本身（代码/SKILL.md） | `git pull` → `python install.py` | **必须重启 WorkBuddy**（技能启动时加载） |
| 数据文件（5 个 json） | 覆盖配置里指的那个文件 | **不用重启**，下次运行就读新版（脚本无缓存） |
| 配置（路径/账号） | 改 `~/.workbuddy/tplink-toolkit.config.json` | 下次运行生效（每个脚本启动时重新读配置） |
| 数据包整体挪了位置 | 重跑一次 `生成配置.py` | 下次运行生效 |

> ⚠️ **配置别写进技能目录的 `config.local.json`**：`install.py` 升级时会删掉整个技能目录再重建，
> 里面的配置会一起没。用用户级 `~/.workbuddy/tplink-toolkit.config.json` 才不受升级影响。

## 🤖 帮用户配好配置（AI 照着做，别让他自己翻文档）

用户说「帮我配一下」「跑起来说找不到控标库」「提示未配置」时，走这五步。

### 第 1 步：先看现状，不许猜

```bash
python ~/.workbuddy/skills/tplink-quote-autofill/scripts/tpkit_config.py
```

第一行 `生效配置文件:` 说明当前读的是哪份；每个字段要么是真实路径，要么是「未配置」/「→ 默认 data 目录」。
**没跑这一步之前不要臆断原因**（是配置没填、路径写错、还是数据文件坏了，三者处置完全不同）。

### 第 2 步：按现状分支

| 现状 | 怎么处理 |
|---|---|
| 全部「未配置」，用户有数据包 | 跑数据包里的 `生成配置.py`，一次把 5 个路径指好（见上一节） |
| 全部「未配置」，用户没有数据包 | 只配他手上有的那几个；**一个都没有也能跑**，先看效果再逐步补 |
| 路径有值但文件不存在 | 问他要正确路径；或临时用 `--kb <路径>` 指定先把流程跑通 |
| 路径有值、文件在、但报数据格式错 | **不是配置问题**，是文件坏了或版本太旧，别改配置 |
| `crm_base` / `dealer_base` 未配置 | 内部域名，仓库里**没有也不该有**，必须问他或同事，**不许猜、不许编** |

### 第 3 步：直接把配置文件写出来（不要让他手抄）

目标文件（用户级，升级不受影响）：

- Windows：`C:\Users\<用户名>\.workbuddy\tplink-toolkit.config.json`
- macOS / Linux：`~/.workbuddy/tplink-toolkit.config.json`

**最小可用模板**——只填用户实际有的，没有的留空串：

```json
{
  "kongbiao_json": "D:/数据/tplink_kongbiao_data.json",
  "dealer_backup_json": "D:/数据/tplink_dealer_backup.json",
  "price_backup_json": "D:/数据/tplink_crm_price_backup.json",
  "license_map_json": "D:/数据/tplink_license_map.json",
  "fw_spec_json": "D:/数据/tplink_fw_spec_20251120.json",
  "weekly_report_root": "D:/数据/周报",
  "crm_base": "",
  "dealer_base": "",
  "crm": { "email": "", "password": "" },
  "dealer": { "phone": "", "password": "" },
  "pricing_default": ""
}
```

写的时候守三条（这三条对应的都是真实踩过的错）：

1. **路径一律用正斜杠**（`D:/数据/x.json`）。反斜杠在 JSON 里必须写成 `\\`，是配错最高发的地方。
2. **目标文件已存在就先读再改**，只动需要动的字段。整份覆盖会把用户已填好的账号冲掉。
3. **拿不到的值留空，绝不填假路径**。留空 → 程序明确提示「未配置」；填一个不存在的路径 → 报「文件不存在」，
   反而更难定位。

每个字段的含义、留空时的默认行为、以及数据文件从哪来，都写在仓库根 **`config.example.json`** 里
（每个字段上方有一条 `_字段名` 注释，JSON 不支持注释所以用这个约定）。

### 第 4 步：验证

再跑一次 `tpkit_config.py`，每个字段都应显示真实路径/地址。然后拿一份真清单实际跑一遍，才算真的通了。

### 第 5 步：把能力边界讲清楚（别让他以为全配好了）

| 配了什么 | 实际能干什么 |
|---|---|
| 只有 `kongbiao_json` | 参数能填；**报价不行** |
| 再加 `crm_base` + `crm` 账号 | 能查标准价、按口径算折扣价 |
| 再加 `dealer_backup_json` | **才做得了选型**（选型前置后这是最关键的一个） |
| 一个都没配 | 也能跑，但参数全走官网、没有价格、没有选型候选 |

## 核心流程

```
读清单 Excel
   │
   ├─ 🄋 【第 0 步 · 所有清单通用 · 最先做】**通读全表，拿到所有信息**
   │     ⚠️ 列位不固定（同一台机器三张清单列位三样），**不许靠列字母认列，也不许"抽样看"**
   │     ① 主表所有行 × 所有列**不截断导出**（openpyxl data_only=True，不预设哪列有用）
   │     ② **通读**：这张表在讲什么？几个系统/多少行/哪些是汇总行/甲方给了什么没给什么
   │     ③ 按**表头文字（语义）**定位各列角色 + 记下哪几列全空（=甲方待我们填）
   │     → 通读没做完，不许进入下一步选型（详见「🅾️ 第 0 步」）
   │
   ├─ ⓪ 【配单前准备 · 所有清单通用】先扫子系统，再问清口径（不默认开工）
   │     ① 扫型号列 → 认出覆盖哪些子系统（网络/监控/广播/门禁/防火墙…）
   │     ② 逐子系统问清口径（选型优先档、价格保护、投标、广播替代、防火墙授权…）
   │     → 用户没说明就必须开口问（见「🛑 动手前必问」）
   │
   ├─ ① 【选型 · 先做】出「选型清单 + 选型依据」→ 【暂停，交用户确认】
   │     ① 先问选型优先档：优先渠道 / 优先项目 / 优先域联（必问）
   │     ② 按「清单型号 + 参数」选型 → 两张表：选型清单（原→建议型号/数量）+ 选型依据（为什么）
   │     ③ 【停】用户确认 / 改型号后才继续（见「🧭 选型阶段」）
   │     ④ 交付后**必须问**「这版有没有要调整的」→ 用户回答后 clear select，否则下一段被挡（见「🔄 每段交付后」）
   │
   ├─ ② 参数列（空才填）—— 用户确认选型后
   │    ① 本地控标库精确匹配型号 → 命中即用（含 ★▲ 加分项）
   │    ② 未命中 → 前缀/包含模糊匹配（控标库有 "TL-VS7500（含…）" 这类长名）
   │    ③ 仍未命中 → 官网 www.tp-link.com.cn 搜型号 → 抓「产品特性」**+「规格参数」能力项**（带机量/三层转发/新建连接速率…），按 1. 2. 3. 编号
   │    ④ 脱品牌：去掉商云APP / TUMS / 算法商城 / TP-SRC / TP-LINK 等字眼
   │    ⑤ 脚本末尾自动打「🔁 交付回执」→ **必须原样转述**，用户回答后 clear（见「🔄 每段交付后」）
   │
   └─ ③ 价格列（空才填）—— 用户确认选型后
        ⓪ 【先问本次定价策略】—— 每次问；**用户未说明 → 用本地配置的默认策略**（见「💴 定价默认策略」）
        ① 先拆组合型号：`A+B*4` → [(A,1), (B,4)]；`A*2` → [(A,2)]
        ② CRM 按**每个配件**的型号查标准价（面价）+ businessDiscount + seriesValue
        ③ 按本次策略算单价
        ④ 算出来的价向上取整到个位 0/2/5；标准价原样保留
        ⑤ 配件单价 × 自身数量，**全部加总**，填入该行的单价列
        ⑥ 同上：回执里第二段问价格口径，**必须问**、必须 clear（见「🔄 每段交付后」）
```

## 🧭 选型阶段：先出「选型清单 + 选型依据」，交用户确认后才往下（2026-10-15 用户明确）

**为什么单独拆出来**：填参数、填价格已经很成熟（脚本化、确定性）；
**选型最灵活、最容易出错**，所以要**先选型、出证据、人工拍板**，再往下走。

### 🅾️ 第 0 步：**配单前的第一件事——通读全表，拿到所有信息**（2026-10-16 用户退回后新增，重要）

> **用户定的顺序（2026-10-16）**：**「列位不固定，所以配单前第一件事就是通读全表拿到所有信息。」**
> 先通读、后选型。**没通读完就不许动手选型**——这是流程的第一步，不是"顺便看看"。

**教训**：人才公寓单（210 行 / 10 子系统）第一版选型只看了「型号规格」列，交上去被用户退回——
**「只依据了 D 列型号规格，F 列技术参数完全没注意吗？清单的每个信息都要读到」**。
根因就是**没通读全表**：只挑了自己以为重要的那列看。

**正确动作顺序**：

1. **全表不截断导出**：用 openpyxl（`data_only=True`）把**主表所有行 × 所有列**原样 dump 成文本/JSON
   —— **不做任何裁剪、不预设哪列有用**。多 sheet 的表要把有内容的 sheet 都 dump。
2. **通读**：从头到尾过一遍，**先不管哪列是什么，先看懂这张表在讲什么**（几个系统？多少行？
   哪些行是汇总/小计？甲方给了什么、没给什么？）。
3. **识别列角色**：通读后按**表头文字（语义）**对各列定位（见下表）；
   顺带记下**哪几列全空 / 哪几列是甲方待填**（这决定后面填哪些列）。
4. **才动手选型**。

> ⚠️ 这一步存在的理由就是**列位不固定**：既然没法靠列字母认列，就只能靠**通读全表**把内容看明白。
> 半途中挑列看 = 又在赌列位，等于没读。

> ⚠️⚠️ **两个常见错误**：
> ① 把「某一单的列字母」当通用规则（**「D 列 / F 列」只是人才公寓那一种表**，技能里
> 「表结构各异的坑」「列位必须显式传」两节都在讲这事）—— 引用它就别在下一段违反它；
> ② 只 dump 表头就开干 —— **表头给的是列名，通读给的是"这列里到底写了什么"**
> （参数列里可能藏着品牌池、口径、甚至自相矛盾的要求，光看表头看不出）。
> 下表按**语义列**列，缺一不可：

| 语义列 | 常见表头写法 | 对本环节的作用 |
|---|---|---|
| 产品/材料名称 | 产品名称 / 项目名称 / 材料名称 / 设备名称 | 判断品类 |
| **型号规格** | 型号规格 / 规格型号 / 型号 | 常常只是"外形/尺寸描述"，**不等于选型依据** |
| **技术参数** | 技术参数 / 参数 / 规格参数 / 技术规格 / 性能参数 | **真正的选型依据，必须逐条对照候选型号规格** |
| 单位 / 数量 | 单位、数量 | 单位错配会让单价口径全错（见「交付前自检」第 3 项） |
| **备注** | 备注 / 品牌 / 品牌要求 / 说明 | 常藏着**「品牌：…」品牌池**与甲方口径（如"取高""双核心冗余"） |

**实证：同一台机器上三张清单，列位三样**——
- 人才公寓单：`A序号 B系统/分项 C产品名称 D型号规格 E品牌 F技术参数 G单位 H数量 I… K单价 … P备注`
- 0914 无线网络设备清单：`A序号 B项目名称 C品牌 D型号 F参数 G数量 H单位 I单价 J小计`
- 智慧医院单：`A序号 B产品名称 C规格参数 D单位 E数量 F单价 G总价 H备注`

→ 所以**永远先通读全表、按语义找列**再动手，别背列字母。

> ⚠️ **参数列常被 print 截断**成几十字符，务必**不截断导出**后再读。
> 人才公寓单的参数列共 129 行有内容；第一版只扫了几行就动手 —— 这是错的。
> **通读时的量级感**：人才公寓单 210 行 × 16 列，全量导出后一次读完完全可行，别"抽样"。

**参数列还会自相矛盾**，遇到要停下来记出来（人才公寓单实测，行号属该单）：
- 「无线控制器」行的参数与「路由器」行**一字不差**（甲方模板复制错误）；
- 「无线 AP」行第 1 条要 `802.11ax`（Wi-Fi6），第 2 条却写「双频五流 1.775Gbps」（Wi-Fi5 规格）。
- 处置：标成**「需确认」交用户**，不要自己挑一条就算满足。

### 🔍 选型取数：本地镜像反查 + 每周刷新（2026-10-18 平台实测）

**选型反查走本地 `tplink_dealer_backup.json`，不是每次登平台。** 原因不是"省事"，是接口能力不匹配：

| 环节 | 平台接口（实测） | 结论 |
|---|---|---|
| 登录 | 0.42s | 快，不是瓶颈 |
| 分页列表 `findProductPage` | 一页约 0.56s，可按类目 / 搜索词 / 预置规格筛 | ✅ 可用 |
| 按型号直查 `findProductPageByModel` | **`-1002 你没有进行该项操作的权限`** | ❌ 该账号无此权限 |
| 产品详情 `productDetail` | 0.29s/条 → 全量 2300+ 条 ≈ **11 分钟** | 只在必要时拉 |
| 全站条数 | 平台 **2346** / 本地 **2816**（多出的是已下架，保留用于查替代/降本） | —— |

**为什么必须本地**：甲方给的是「400万 PoE 双光全彩 4mm 筒机」这样的**要求**，
要回答"哪几款满足 / 同档还有哪些替代 / 这个系列全量几款"——是多维属性**交叉过滤 + 集合运算**。
平台的 `specsFilterList` 是预置筛选维度，表达不了自由参数组合；按型号直查又没权限。

**每周刷一次**（平台数据会变：新品上市、老品下架、类目调整、名称错字修正）：

| 命令 | 耗时 | 什么时候用 |
|---|---|---|
| `python backup.py refresh` | 约 20 秒 | **每周常规**：只拉列表，更新在售/停产/行业/类目，新增型号才补详情 |
| `python backup.py refresh --deep` | **5~15 分钟** | 每月一次，或要重做选型规则时：**全量重抓**平台详情 + 官网规格 |
| `python backup.py stats` | 秒级 | 看上次刷新时间 / 下架清单 / 停产数 / 数据完整度 |

`refresh`（默认档）做与不做：

| 做 | 不做 |
|---|---|
| 拉全站列表（53 个品类、约 2800 行，20 秒） | ❌ 不重拉已有型号的 `desc` / `spec` |
| 更新在售/停产/行业/类目/价格量级（**列表行就带，不用拉详情**） | ❌ 不删除消失的型号，只打 `missing_since` |
| **新增型号**才拉详情 + 官网规格（一般每周几条） | ❌ 一次消失 > 10% 时**不打标记**（防漏页/权限变动误判） |

> ⚠ **为什么要专门做 `refresh`**：`all` 的断点续跑按「已有 desc+spec」跳过，
> 已入库型号**永远不会被重新抓** → 平台后来改的 `haltProduct` 会丢。
> 走列表行更新绕开了这个坑，不拉详情也能把停产状态刷对。
> `--deep` 则是显式关掉断点续跑，把已有型号也重抓一遍。

### 本地每条记录里有什么（选型取数就看这些）

| 字段 | 内容 | 选型用途 |
|---|---|---|
| `spec` | 官网规格，**三级完整**：`group`（大分组，如「图像与视频参数」）+ `name`（子分组，如「基本参数」）+ `values`（「传感器类型：1/3英寸CMOS」这种名值行） | 参数列的主要来源 |
| `desc` / `spotlight` | 平台产品描述 / 官网卖点 | 参数兜底、判断产品定位 |
| **`siblings`** | **同系列型号清单**（平台 `productGroupList`） | 直接回答「这个系列还有哪几款」，不用再搜一遍 |
| `detail_raw` | 平台详情**全部非空字段**（约 23 个：`catalogPrice` `boxNumber` `newProduct` `haltProduct` `bargainClearance` `virtualProduct` …） | 判新品/清仓/停产、查装箱数、以后要用新字段不必重抓 |
| `halt` / `industry` / `cat1` `cat2` | 停产 / 行业产品 / 类目 | 选型优先档的库判据 |

> 2026-10-19 起 `spec` 才带上大分组 `group`——此前 `flatten_spec` 读的字段名是 `speGroupName`，
> 官网实际叫 `spe`，导致 group 全空、分组信息丢失。
> **只有 `refresh --deep` 能把已有型号的这些字段补齐**；普通 `refresh` 只对新增型号生效。

**全量深抓后的数据完整度**（2026-10-19 实测，供判断"是不是抓漏了"）：

（2026-10-18 就刷出 `TL-IPC445FP-W6` 半球新焦距，推翻了"F 系半球只有 W4/2.8"的旧结论）。

**但 `lifeCycle` 停产核验仍是固定步骤，走 CRM**（见「🚨 选型类任务」）——
`refresh` 只反映"平台上不出现了"，不等于 CRM 里的停产/退市状态。

### 选型阶段做什么

1. **先问选型优先档**（必问，见「🛑 动手前必问」）：**优先渠道 / 优先项目 / 优先域联**？
2. 按「清单型号 + 参数要求」选出建议型号（标准一 / 标准二 见「🎯 选型的两套标准」）。
3. **产出两张表**交给用户：

**表 A · 选型清单**

| 行号 | 原清单型号 | 数量 | 建议型号 | 数量 | 变化 |
|---|---|---|---|---|---|
| 12 | （甲方给的型号/参数） | 8 | `TL-IPC544FP-W4` | 8 | 按参数替换 / 原样 |

**表 B · 选型依据**（逐行讲清"为什么选它"，这是重点）

| 行号 | 选定型号 | 选型依据 |
|---|---|---|
| 12 | `TL-IPC544FP-W4` | 甲方要"400万 PoE 双光全彩 4mm 筒机"→ F 系筒机 400万 4mm 双光全彩；命中参数：像素/供电/形态/焦距 |

- 依据要写清：**命中甲方哪几条参数**、**为什么是这个系列**、**有无替代/风险**
  （如 F 系无红外版，要红外就得退回 G 系）。

### 🚦 闸门：选型阶段结束必须停

- 出完 A / B 两表 → **暂停**，交用户（本人）**确认 / 改型号**。
- **用户确认前，不得进入参数列、价格列**（否则选型一变，参数价格全白填）。
- 用户改了型号 → 以用户为准，再往下。

> 一句话：**选型 = 先给方案 + 依据，人工确认后再落地。** 不是闷头把整张表填完。

## 🔄 每段交付后：问反馈 → 判断要不要沉淀（2026-10-19 用户明确，同日加机械闸门）

**两段式不是"交完就等下一句"**。选型、参数、价格，**每交付一段都要主动问一次**，
用户提了修改就去改，改完**再判断这条值不值得写进 skill**。

> **为什么加了闸门**：用户原话「能不能保证别人用的时候，每次用完都会和我互动、
> 请求修改意见并询问是否更新 skill，这个很重要，一定要强约束」。
> 光写"记得问"没用——模型会跳过去。所以做成**代码断点**（`scripts/deliver_gate.py`）。

### 〇、闸门机制（先看这个，不然会被卡住）

| 时机 | 谁在做 | 发生什么 |
|---|---|---|
| `pick.py` 跑完 | 脚本自动 | 记「选型待确认」，打一行提示 |
| `autofill_quote.py` 跑完 | 脚本自动 | **最后一块**打印「🔁 交付回执」，里面是必须原样转述的问句 |
| 想跑下一段 | 脚本自动 | 上一段没 clear → **stderr 报错 + 退出码 3**，直接不干活 |
| 用户回答之后 | **你** | `python deliver_gate.py clear <段> --verdict ok` |

```bash
# 卡在哪一段
python deliver_gate.py status --project "某清单"

# 用户说没问题
python deliver_gate.py clear params --verdict ok --project "某清单"

# 用户说这段不用看（只在他明确这么说时用）
python deliver_gate.py clear params --verdict skip --project "某清单"
```

**`--project` 两边必须指向同一个清单**：`pick.py --project "某清单.xlsx"` 和
`autofill_quote.py --xlsx "D:\...\某清单.xlsx"` 会归一化成同一个 key
（取文件名、去扩展名）。**对不上 → 门禁不触发 → 反馈闭环直接断掉**。

**能绕过吗**：`--no-gate` 可以，但**只给批量重跑 / 调试用**。
给用户跑正式单子时加 `--no-gate`，等于亲手关掉反馈机制——不要这么做。

**`clear` 只能在用户真实回复之后调用**。替用户说"应该没问题"然后 clear，
是这套机制里最坏的一种作弊：流程显示走完了，实际一条反馈都没收到。

### 一、三个交付点，各问一句（固定问法，别含糊带过）

| 段 | 交付物 | 必须问 |
|---|---|---|
| ① 选型 | 选型清单 + 选型依据 | **「这版选型有没有要调整的？型号、数量、档次都可以改。」** |
| ② 参数 | 参数列 | **「参数有没有要改的？哪几条写得不对或不够？」** |
| ③ 价格 | 单价 / 小计 | **「价格口径对不对？折扣档、取整、License 年限要不要调？」** |

问的时候**顺带给出可调项**（"这 3 个型号我按 F 系选的，要 G 系我可以换"），
不要只丢一句"有问题吗"——那样用户往往想不起来该看哪儿。

### 二、收到反馈：先分类，再动手

| 反馈类型 | 特征 | 处理 |
|---|---|---|
| ① **这一单的个例** | 只跟这个项目/环境有关（"这台装室外要防水"） | 直接改这一单，**不动规则** |
| ② **某个型号数据不对** | 参数写错 / 查不到 / 停产没标 | 先查数据源核实；属实的改本单，再判是否属 ③ |
| ③ **通用规则缺失或写错** | 换个清单也会犯同样的错 | 改完后**问用户要不要沉淀进 skill** |

判断口诀：**"下次做别的单还会不会犯"** —— 会 → ③，不会 → ①。

### 三、要沉淀时，怎么问、怎么落

**问法（原话级别，不要自己决定）**：

> 这条看着不是这一单的事，是个通用规则。要我写进 skill 吗？
> 写的话要改两处：本机技能目录 + 仓库源码；仓库那份**得你确认才提交**。

**用户说"要"之后的动作顺序**：

1. **改仓库 clone 的那份**（`tplink-quote-toolkit/skills/...`），
   ❌ **不要直接改 `~/.workbuddy/skills/`** —— 那是 `install.py` 装出来的副本，
   下次重装会 `rmtree` 整个删掉重建，改动会静默消失
2. 同步到本机技能目录，**两侧 diff 必须为 0**（改了源不同步 = 两份说法打架）
3. **提交前必须先问用户确认**——这是硬规则，不许自作主张 commit
4. 提交 → 推送 → 同事 `git pull` + `install.py` + 重启 WorkBuddy 才能拿到

**三条硬边界**：

- 写进 skill 的规则/数字**必须有可指认来源**（控标库、CRM、官网、平台实测），
  **没来源的一律不写**，或标「⚠ 待补：需要 X 型号在 Y 场景下的实测数据」
- 用户说"不用沉淀"就**到此为止，不要追问第二遍**
- 沉淀的是**规则**，不是把这一单的具体客户信息写进去（客户名一律泛称）

### 三之二、反馈必须落成 Issue 素材（不然等于没提）

**问题**：同事在对话里说"这个型号选错了"，说完就消失在聊天记录里——
作者收不到，下一个人还是踩同一个坑。**反馈不变成可追溯的东西，开源项目就转不起来。**

凡是「换个清单还会犯」的反馈，都要跑一次：

```bash
python deliver_gate.py issue --stage params \
    --title "一句话说清问题" \
    --detail "怎么复现、当时的原始输出是什么" \
    --expect "你期望它怎么做" \
    --severity 严重 \
    --project "某清单"
```

生成标准 Markdown（问题 / 复现信息 / 具体现象 / 期望行为 / 建议改哪里），
存到 `~/.workbuddy/tplink-toolkit/feedback/`，并**把全文打在屏幕上**。

**两条出口，按同事的情况选**：

| 同事情况 | 怎么提交 |
|---|---|
| 有 GitHub 账号 | 仓库 → Issues → New issue → 粘贴 → 提交 |
| 不想碰 git | 把那段 Markdown 直接发给作者（微信 / 邮件都行） |

提交后标记：`python deliver_gate.py submit <序号>`
查看未提交：`python deliver_gate.py feedback`

> **为什么非要是 Issue 而不是聊天记录**：Issue 有编号、有状态、能被搜到，
> 修的时候能引用（`fixes #12`）。聊天记录里说一百遍，等于零。

### 四、提交权限：改动必须经仓库所有者审核

**用户口径（2026-10-19）**：「提交的话应该不是他提交我就修改了吧，我应该会有一个审核吧」

**是，有审核，这是 GitHub 的默认机制**：

| 谁 | 能做什么 |
|---|---|
| 仓库所有者（本人） | 直接 push main |
| 其他人（同事） | **对 main 没有写权限** → 只能 Fork → 改 → 提 **Pull Request** |
| PR 合并前 | 改动只存在**他自己的 fork** 里，**不影响任何人的技能** |
| PR 合并后 | 所有者 review 通过才合进 main，其他人 `git pull` 才拿得到 |

所以流程是：**同事提 PR → 所有者看 diff → 认可才点 Merge → 才算进了主线**
（可以在 GitHub 仓库 Settings → Branches 给 main 加保护规则，强制走 PR，见 README）。

⚠️ **两种情况会绕过审核，要避免**：
- 把同事加成 Collaborator（有写权限就能直接推 main）
- 同事把改动只改在自己 `~/.workbuddy/skills/` 里，以为"大家都更新了"——**实际只有他一个人变了**，
  下次重装还会被覆盖

## 📝 参数来源与写法：控标库优先，官网兜底必须补「能力项」（2026-10-15 用户明确）

**用户口径**：参数列填的一直是**控标参数**（投标控标口径），不是随便抄官网营销词。
控标库没有该型号时才去官网抓「产品特性」，抓完**必须脱敏**（见「品牌词中性化」章节）。

### 官网兜底：不能只抄「产品特性」，要补「规格参数」里的能力项

官网产品页有两块内容，**别只抄营销块**：

| 块 | 内容 | 怎么用 |
|---|---|---|
| 「产品特性」 | 营销文案（"高速转发""智能管理"…） | 可用，但**必须脱敏** |
| 「规格参数」 | **规格表**（端口、带机量、转发性能…） | **必须挑出能体现产品能力的项写进去** |

**关键规则**：有些产品（尤其**路由器**）「产品特性」里**不写带机量**，但规格表里有 → 这种情况：

- ✅ **务必把带机量写进参数**（数值以官网「规格参数」表为准，**不要自己估/编**）
- ✅ 同一类别推：**三层转发能力 / 新建连接速率 / 并发连接数 / 无线速率 / 端口规格** 等
  能表达该产品规格的项，都要从规格表挑出来写进去
- ✅ **按 1. 2. 3. 4. 编号**写成**分条**，和控标参数**同一个格式** → 达到**统一的效果**

> **为什么**：投标时评委按条对参数，只写"支持智能管理"这种营销词 = 无量化项可核对 = 等于没响应。
> 路由器写"推荐带机量 N 台 / 三层转发 / 新建连接速率 N"才是实质响应。

### 格式统一：两种来源，输出必须长得一样

| 来源 | 原始形态 | 写入参数列前 |
|---|---|---|
| 控标库命中 | 已是**分条编号**（1. / 2. / 3. …，含 ★▲ 加分项） | 直接用 |
| 官网兜底 | 「产品特性」**整段营销文字** | 摘录 + **补齐规格表能力项** + **重排成 1. 2. 3.** |

**底线**：参数列最终必须是**分条编号**格式，条与条用 `；` 或换行分隔——
**不能一边是分条、一边是整段文字**（否则同一份清单风格不一，投标观感差）。

## 折扣换算方法（长期有效，可复用）

### 1. 三档折扣率的关系

CRM 里每个型号带一个**业务折扣率**（`businessDiscount`）。由它可换算出另外两档：

| 业务折扣率 | 片区折扣率 | 总部折扣率 |
|---|---|---|
| 0.45 | 0.43 | 0.40 |
| 0.43 | 0.40 | 0.40 |
| 0.39 | 0.34 | 0.32 |
| 0.32 | 0.27 | 0.25 |

**折扣价 = 标准价 × 折扣率**

- **业务底折价** = 标准价 × 业务折扣率（业务员底价口径）
- **片区折扣率 / 总部折扣率**：对外报价常用的两档，按上表由业务折扣率换算。
- 表里查不到 `businessDiscount`（如 0.40 / 0.35 等意外值）→ 取标准价，并提示用户确认。

### 1.5 渠道产品 vs 项目产品（用户 2026-09-22 明确，**记住**）

用户的原话口径：**「没有业务折扣的就是渠道产品」**。

| 判定 | CRM 特征 | 取价 |
|---|---|---|
| **渠道产品** | `businessDiscount` 为 **null / 空** | **直接取面价（标准价）**，不参与任何折扣 |
| **项目产品 / 行业产品** | `businessDiscount` **有值**（0.45 / 0.43 / 0.39 / 0.32） | 按本次口径走片区 / 总部折扣 |

- 实际与「`seriesValue == '项目机型'`」高度重合，但**以 `businessDiscount` 有无为准**（用户口径）。
- 实测（0922 保税区跨境电商园 26 型号）：14 个渠道产品全是空 `businessDiscount`，
  12 个项目机型全带值。渠道产品里既有监控件（摄像机、光模块、支架）也有网络件（交换机、
  收发器、网线），**不能按品类猜，只能看字段**。

### 2. 哪类产品用哪档：按「项目机型」判断

- **只有 `seriesValue == '项目机型'` 的型号有业务折扣**，才有资格走片区/总部折扣；
- 其余系列（`域联产品` / `双频AP` / `其他附件` 等）**没有业务折扣，直接取标准价**。

> 这是**型号属性层面的通用规律**（CRM 数据本身如此），不是某次商务决策。
> 但**具体某单给片区还是总部、给几个点，仍由用户每次指定**。

### 3. 片区 / 总部怎么分（型号类别）

| 类别 | 走哪档 |
|---|---|
| 监控类：摄像机、NVR/存储、解码器/矩阵、拼接控制器、综合管理一体机 | **片区折扣率** |
| 其他类：交换机、AP、AC、路由器、门禁梯控道闸、拼接屏 `TL-VE`、网络控制键盘 `TL-NK2000` | **总部折扣率** |

型号前缀速查：
- 片区：`TL-IPC` `TL-NIPC` `TL-AIPC` `TL-NAIPC` `TL-NVR` `TL-NVS` `TL-NVD` `TL-NVDU` `TL-VS` `TL-SDC` `TL-TUMS`
- 总部：`TL-KBG` `TL-EC` `TL-EML` `TL-EBL` `TL-AH` `TL-AS` `TL-CR` `TL-CW` `TL-DEB` `TL-CARD` `TL-VE`

> ⚠️ 两个易搞反的：**拼接屏 `TL-VE`** 虽属监控系统但走**总部**；
> **网络控制键盘 `TL-NK2000`** 同理走**总部**。
>
> ⚠️ **「网络类走哪档」不是固定的，会随单变化，必须每次问。**
> 上表把交换机/AP/AC/路由器放在总部，但 2026-09-22 保税区跨境电商园那一单，
> 用户明确指定 **「监控和网络用片区折扣，门禁和停车总部折扣」**——
> 网络被划进了片区。别照搬上表，以用户当次口径为准。
>
> ⚠️ **显示器 / 拼接屏走总部**（用户 2026-09-22 再次确认「显示器走总部折扣」）。
> 判据是"显示类"这个属性，不止 `TL-VE` 拼接屏；22 寸监视器 `TL-LM1022` 这类也归显示。

## 折扣口径：每次问用户，不预设（重要）

上面给的是**换算方法**（怎么算、哪档对应哪类）。
**但"这一单到底给几折"是商务决策**，随项目/客户/时间变化，
必须**每次开工前向用户确认**，不要沿用上一次会话的结论。

开工前问清这几条：

1. **哪些型号走折扣？** 例如「只有项目机型走折扣」／「全部都走折扣」／「这些都按标准价报」。
   - 常见默认口径是「只有 `项目机型` 走折扣」，但**仍要问一句确认**，别自己定。
2. **给哪一档、几个点？** 例如「项目机型走片区」／「一律总部」／「统一 0.34」。
   - 用户也可能直接给一张"业务底折率→折扣率"的对照表，**以用户当次给的为准**。
3. **非折扣型号怎么取价？** 通常是取标准价（面价）原样保留。
4. **要不要加点？**（用户有时要求"加几个点"）加了点产生小数同样向上取整。

> 若用户说「还是按上次的口径」，先去翻上次的台账/产出确认具体数值，**复述一遍让用户确认**再算。

### CRM 取价字段（这部分是稳定的技术事实，可长期复用）

| 字段 | 含义 |
|---|---|
| `price` | **标准价**（面价）——对外报价无折扣时直接用它 |
| `businessDiscount` | 业务折扣率（仅部分型号有，非空才可能打折） |
| `seriesValue` | 系列值，如 `项目机型` / `域联产品` / `双频AP` / `其他附件` |
| `productModel` | 型号（**模糊匹配**，客户端必须按精确型号再筛一遍） |

- 登录/查询接口见 `references/crm_access.md`。
- 同一型号可能返回多条（不同 OU/区域/版本）→ **全部列出，交用户裁决**，不要自己挑一条。

## 🔐 授权类 SKU：多合一特征库怎么取（2026-10-13 用户亲授 + 官网实测）

**防火墙（TL-FW / TL-NFW / YLFW）和上网行为管理（TL-NASG）用的是同一个「多合一特征库」**，
但买到哪个 SKU、多少钱一年，**由产品自己的规格决定**，不是按产品线或价格档分：

| SKU | 年费 | 对应平台 |
|---|---|---|
| `TL-FW-LIS-ALL` | **200 元/年** | 老平台，内存普遍 ≤ 2GB DDR4 |
| `TL-FW-LIS-ALL-E` | **800 元/年** | 新平台，内存普遍 ≥ 4GB DDR4 |

### 权威查法（唯一可靠）：查官网产品规格里的分组名

官网产品页「规格参数」里有一组 **`License授权（<SKU>，多合一）`**，**SKU 就写在分组标题里**：

```bash
# 工具（离线缓存优先，缺失才联网）
cd "<控标数据目录>\dealer-tool"
python license.py TL-NASG6003 TL-FW5800 --price     # 查型号 + 年费
python license.py --all                             # 全量刷新安全类映射表
python license.py --list                            # 只看本地映射表（离线）
```

底层接口（如需自己抓）：
`https://www.tp-link.com.cn/publicservice/productinfo?brand=TPLINK&productModel=<officialRelateId>`
→ 解析返回的 `specification`（JSON 字符串），找 `[].spe` 含 `License授权` 且含 `多合一` 的分组，
**分组名含 `-E` → 800；不含 → 200**。

### ⚠️ 三条硬约束

1. **必须逐型号查，不能按系列外推**。同系里混着两种：
   `TL-FW5800`(2GB)=200 而 `TL-FW5900`(4GB)=800；
   `TL-NASG5003/5005`(2GB)=200 而 `TL-NASG5007/6003/6007`=800。
2. **官网没写 SKU 的分组名只写「License授权（多合一）」**（如 `TL-NR4914` 系列）→ 用内存档位推测并**标注待确认**：
   ≤2GB→200（NR4914-L/M）、≥4GB→800（NR4914-S）。**不许当已确认结论用**。
3. **没有 License 授权分组 = 不支持多合一库**，别硬加：
   `TL-NR510-2C-S`（融合安全网关）、`SAR500G`（安全审计路由器）。

### 计价要点

- IPS/AV/恶意域名等库**出厂均无授权**，客户要"特征库在线更新"就必须**另购多合一授权**，
  按**台数 × 年数**算，且 **授权不打折、本体才打折**（先折算本体、再加授权）。
- 买了多合一**不能与单个库混搭**（单买五库 4200 元 vs 多合一 800 元，价差巨大）。
- 全量库清单（多合一涵盖）：IPS库 / AV库 / 恶意域名库 / 应用库 / 网站库。

### 默认配置：3 年多合一库授权（2026-10-15 用户新规）

**防火墙参数清单里没有特殊说明时，默认加 3 年多合一库授权**。
两种 SKU 见上表：`TL-FW-LIS-ALL`（200/年，老平台）或 `TL-FW-LIS-ALL-E`（800/年，新平台）—— 选哪个按本机内存档（≤2GB→ALL，≥4GB→ALL-E），**不能按系列外推**（见上面三条硬约束）。

- **型号列写法**：`防火墙型号+TL-FW-LIS-ALL-E*3`（用 `+` 和 `*3` 走组合型号解析，见「组合型号」章节）。
- **价格列**：本体折扣价 + License 单价 × 3，**授权不打折**（先折算本体、再加授权）。
- **参数列**：把"含 3 年多合一特征库授权（IPS/AV/恶意域名/应用/网站）"写进响应参数。
- **例外**：用户明确说"不含授权"或"客户自己买" → 跳过并在 `--report` 标注「用户口径：无授权」。
- 用户问"防火墙多少钱" → 报价 = 本体折扣价 + License × 年数。

## 🧩 框式交换机：机框是「裸机框」，主控 / 业务板 / 电源全要另配（2026-10-16 实测 TL-NS7906E / NS7606E）

**机框本体要什么没什么**：没有业务口、没有主控、没有电源。
选型库产品描述里明写「**业务板、主控板、电源模块需单独购买**」。
只写机框 = 交不出网口 + 没主控 + 没电，是**三重漏配**。

> 两次踩坑：1013 清单只填 `TL-S7803E` 没填板卡；261014 清单三个核心交换机只填 `TL-NS7906E` 机框，
> 主控 / 业务板 / 电源全漏，**被用户连着指出两次**。

### 铁律一：**通读全部参数**，把「本次配置：…」那段端口清单找出来

招标的核心交换机参数里常有一段形如
「**本次配置：双主控，双电源，单风扇，48千兆电口，48个千兆光口，8个万兆光口**」的文字 ——
**这段是采购配置的硬依据**，端口数量与类型按它逐项配。

⚠️ **它不一定在最后一行**：可能夹在中间、可能和别的条目混排、也可能没有小标题。
**必须通读全部参数逐条找，不能只扫末行。**

⚠️ **反过来也不能认为"前面的条目只是通用能力、不决定采购配置"**。
前文那些条目（端口速率、PoE、主控/电源冗余、业务槽数量、协议与管理方式等）
**同样决定采购配置** —— 前文与「本次配置」段**都是本项目的具体化要求**，要逐条对照。
唯一"只提示、不作门槛"的只有铁律三点明的那两项容量类指标。
**别把"找本次配置"变成"只读本次配置"。**

> 261014 那单就是漏看了这段，结果千兆电口、千兆光口**全为 0** —— 不是差几个口，
> 是**端口类型整块错**。**做框式必通读参数、锁定「本次配置」段。**

### 铁律二：端口是**物理独占**的，不能"一鱼两吃"

「万兆口向下兼容千兆模块」只意味着**该口可以插千兆模块来用**，
**不代表它同时还能当万兆口**。响应「X 个千兆光口 + Y 个万兆光口」必须按
**X + Y ≤ 光口总数** 核算，并分清端口**原生**速率是什么。

> 261014 踩坑：误以为一块 48 万兆口板能同时顶「48 千兆光 + 8 万兆」，
> 实际 48 个口塞不下 56 个需求，**必须两块板**。

### 铁律三：**交换容量 / 包转发率**不作为选型依据（2026-10-16 用户口径）

用户明确：**「交换机只要端口够了，交换容量和包转发率可以不用管」**。
即**只**这两项：**端口满足即为实质性响应**，它们**不计入选型门槛**；
官网标称值低于招标要求 → **照样标红**（供评标答疑用），但**不因此换型号**。

⚠️ **不要把这条扩大化**：它只覆盖**交换容量**和**包转发率**。
MAC 地址表、设备高度、带机量、PoE 功率等**其他**硬件指标**仍需逐项核**；
拿不准的标橙问用户，别拿这条当"什么都可放过"的挡箭牌。
详见「🎯 选型的两套标准」章的「哪些硬件参数算实质性」小节。

### 电源与功耗怎么定（2026-10-15 官网实测）

- **功耗表在官网规格页的「板卡推荐」栏**（不在选型库里）：
  `www.tp-link.com.cn/product_<id>.html?v=specification`
- TL-NS7906E 实测：主控 `TL-NS7900E-MPUA` **38W**；业务板 `48S` **70W**（满插万兆**光**模块）/
  **180W**（满插万兆**电**模块）；`48G2S` **45W**；**机框固定 238W**
- **算法**：整机最大功耗 = 主控×n + 业务板×n + 238W；官网要求「**电源输出总功率 > 整机最大功耗**」
- 电源 800W / 1600W 两档，TL-NS7906E 有 **4 个系统电源槽**；**多电源必须同型号**
- 实算：2 主控 + 1×48S（满插光模块）= 76 + 70 + 238 = **384W** → `800W×2 = 1600W` 足够，**不必上 1600W**
- **风扇模块是机框标配，不用另配**；只有主控 / 业务板 / 电源要买

### 实操要点

1. **「平台支持 N 种业务板」≠ 要买 N 块板**。招标写「支持不少于三种业务板…」属**能力 / 控标项**，
   答标列出可支持的板卡清单即可，**不需要采购**；只有清单写「加装 / 配置 / 含 XX 板」的才要买。
   同一行里两种口径常同时出现，必须分开处理。
2. **按端口数对端口数映射，不要按名字猜**。TP 没有的 SKU 就用端口能力更接近的板上顶（超配无妨），
   但**不能拿一批物理口去顶两批不同速率的需求**（见铁律二）。
3. **省板 vs 满配，报给用户定**，不要自己拍。
4. ⚠️ **板卡页与机框页口径可能不一致**：兼容性**以机框页规格表为准**，被质疑时用它举证。

## 组合型号：参数取主型号，价格必须加总（重要）

型号列里经常写成一整套配置，**不是单个型号**。这类行必须拆开算：

| 写法 | 含义 | 参数填谁 | 价格怎么算 |
|---|---|---|---|
| `TL-VS7500+TL-NVDU7606S*4` | 1 台解码矩阵 + 4 块业务板卡 | **TL-VS7500** | 9720 + 2484×4 = **19656** |
| `TL-EML100+TL-EML100-LZ` | 1 把锁 + 1 个 LZ 型支架 | **TL-EML100** | 100 + 50 = **150** |
| `TL-EBL100+TL-EBL100-U` | 1 个电插锁 + 1 个下门夹 | **TL-EBL100** | 80 + 25 = **105** |
| `TL-FC311A-3/TL-FC311B-3` | 收发器 A/B 一对 | **TL-FC311A-3** | 74 + 74 = **148** |
| `TL-EC100-M18*2` | 单个型号 ×2 | TL-EC100-M18 | 702×2 = **1404** |

规则要点：

1. **参数只取第一个（主）型号**的控标参数，副件不参与参数。
2. **价格把所有配件加总**。每个配件**各自按用户指定的口径**算单价（配件可能一个打折、一个不打），
   再乘自身数量，最后相加。
3. **数量后缀 `*N` / `×N` 紧跟在型号后面**，只作用于紧邻的那个型号：
   `A+B*4` = A×1 + B×4，不是 (A+B)×4。
4. **`*N` 也要能识别单型号行**：`TL-EC100-M18*2` 是「一个型号买 2 个」，单价列填 2 倍价（1404）。
5. 函数：`parse_combo(型号串)` → `[(型号, 数量), ...]`；`parse_combo_first(型号串)` → 主型号；
   `is_combo(型号串)` → 是否组合行；`combo_total_price(op, 型号串, rate_spec)` → `(总价, 配件明细, 错误)`。
6. 组合里**任一配件查不到 CRM 价就不填**，在台账里标 `note`，不要只填一半。
7. **改完用自测兜底**：`python scripts/autofill_quote.py --selftest` —— 不联网，断言
   「解析正确 + 组合价必须是加总」，防止逻辑被改回去。

> ⚠️ **型号名里合法出现的 `/` 不是组合分隔符**。实测坑：
> `TL-AP1206GC-PoE/DC易展版` 的 `/DC` 是电源规格后缀，早期版本按 `split('/')` 拆成
> `TL-AP1206GC-PoE` + 空串，直接查不到 CRM 价。
> 现已修复：`/DC`、`/AC`、`/POE` 等后缀（可跟「易展版」）会**并入前一个型号**，
> 且**保留原样斜杠**去查 CRM（CRM 里的型号名本身就带 `/`，换成 `-` 反而查不到）。
> 真·双型号 `TL-FC311A-3/TL-FC311B-3` 不受影响。

### ⚠️ 型号尾部带**半角括号后缀**时，数量后缀会静默失效（2026-09-30 智慧医院单实测，已修）

型号名里的 `(F)` / `(UN)` 这类**半角括号是型号本身的一部分**（CRM 真名就叫
`TL-PSM550-AC(F)`）。旧 token 正则 `TL-[A-Za-z0-9\-\x02]+` 不认 `(`，于是：

```
清单写           TL-PSM550-AC(F)*2
旧解析成          ('TL-PSM550-AC', 1)     ← 括号只截断，紧跟的 *2 也一起失效
应为              ('TL-PSM550-AC(F)', 2)
```

**危险点**：`TL-PSM550-AC` 在 CRM 里查得到（同价 2850），所以**不报错、不提示**，
只是静默少算 1 个配件（本单少 969 元）。又是「查得到所以更危险」那一类。

**修复**：token 正则允许型号主体后跟一个 1~6 位半角括号组：

```python
_MODEL_TOKEN = re.compile(
    r'TL-[A-Za-z0-9\-\x02]+(?:\([A-Za-z0-9]{1,6}\))?(?:易展版|易展)?', re.I)
```

只认**半角 + 字母数字**，所以控标库里的全角注解 `TL-VS7500（含业务板卡）` 不会被吃掉
（那条走 `kb_lookup`，不走 `parse_combo`）。自测已加 3 条断言锁住。

### ⚠️ 型号带中文后缀时，`parse_combo` 会截断，且**静默查到另一个物料**（2026-09-30 实测）

`_MODEL_TOKEN = TL-[A-Za-z0-9\-\x02]+` **不认中文**。型号写成 `TL-SG2216工业级`、`TL-SG2210工业级`
这类带中文后缀的形式时，token 只截到 `TL-SG2216`，于是：

| 清单写的 | parse_combo 截成 | 实际查到 | 真身 | 面价差 |
|---|---|---|---|---|
| `TL-SG2216工业级` | `TL-SG2216` | Web管理交换机 | 工业级交换及光网 `TL-SG2216工业级` | 198 vs **810** |
| `TL-SG2210工业级` | `TL-SG2210` | Web管理交换机 | 工业级交换及光网 `TL-SG2210工业级` | 198 vs **720** |

**两个都是 CRM 里真实存在的在产物料，所以不报错、不报"查不到"，直接按错的那个算** ——
比查不到危险得多（价格差 4 倍）。而且这类型号 `businessDiscount` 为空（渠道件），
一旦套上面价口径就会整行错。

**解法**：先用「单型号快路径」判一遍 —— 若整串以 `TL-` 开头且**不含 `+ / × *` 和换行**，
就**整串原样**去查 CRM，不要走 `parse_combo`。参考实现：

```python
_SEP = re.compile(r'[+/×*]|\n')
def split_models(ms):
    s = str(ms).strip()
    if s.upper().startswith('TL-') and not _SEP.search(s):
        return [(s, 1.0)]          # 含「工业级」等中文后缀的整串，原样查
    return parse_combo(ms)
```

同理，`TL-SG2210R工业级`（900）、`TL-SG2210P工业级`（760）也是独立在产物料，
模糊搜 `SG2210` 会一次返回 14 条，**必须靠精确名分辨**。

**一句话记忆**：**参数认第一个，价格全加总；折扣口径每次问。**

**补一句**：**单型号整串原样查，别让正则吃掉中文后缀。**

### ⚠️ 更隐蔽的一层：`_boundary_ok` 曾把中文后缀当"字母数字"，前缀回退被静默挡掉（2026-09-30 智慧医院监控单实测，已修）

CRM 里带中文后缀的物料名不少：`TL-E521套装`（电梯专用无线网桥）、
`TL-E501固定端&TL-E501轿厢端套装`（电梯监控网桥套装）……

走 `parse_combo` 会截成 `TL-E521`，精确匹配落空后本应走**唯一前缀回退**，但旧写法：

```python
return (not rest) or (not rest[0].isalnum())   # ← 中文的 isalnum() 也是 True
```

`'TL-E521套装'` 的 `rest = '套装'`，`'套'.isalnum()` → **True** → 判成"边界不干净" →
回退被拒 → `crm_price` 返回空 → 上层只报「TL-E521 未查到该型号」，
**整行单价填不出来**（不报错、不崩，就是没价）。

**修复**：只对 **ASCII** 字母数字设防（中文后缀属合法型号后缀）：

```python
def _boundary_ok(k, c):
    rest = k[len(c):]
    if not rest:
        return True
    ch = rest[0]
    return not (ch.isascii() and ch.isalnum())   # 中文/符号后缀放行
```

`TL-SG2210P` vs `TL-SG2210` 的保护**不受影响**（`P` 是 ASCII 字母 → 仍拦截）。
自测已锁 2 条断言（`TL-E521套装` 放行、`TL-SG2210P` 拦截）。

## 清单「没有型号列」时怎么填（2026-09-30 智慧医院监控单）

有的清单甲方直接给了**详细规格参数**、却没有型号列。智慧医院单的 `8.监控` 表头是
`A序号 B产品名称 C规格参数 D单位 E数量 F单价 G总价 H备注`，且 `G = E*F`（公式）。

**做法**：把「型号 + 参数」一起写进 **C 列「规格参数」**（表头既然叫"规格参数"，
本就是报价方填响应参数的位置），并**先把甲方原文备份**（如 `_backup_8监控_原参数.json`）。

```
【C 列写法】
TL-NIPC5478P-W4
1、最高分辨率2560*1440@25 fps…
2、…
```

三点注意：
- **甲方原文常带品牌指向词**（"海康威视臻全彩"、"颜色：海康白"），替换后统一过品牌词中性化；
  连**未响应行**里残留的也顺手改掉（只换词、不动其余文字）。
- **未响应行**（普联无在产对应产品的：线材、支架、电源、硬盘、42U 机柜、操作台…）
  **保留甲方原文、不要硬凑型号**，交付时逐行列出来。
- 写值用**原单元格的 s 索引**（`cell_style(xml, 'C5')`）**零样式改动**，styles.xml 一字节都不用动。

## 📷 摄像机型号认法：系列字母 + PoE + 焦距（2026-10-14 用户亲授，2026-10-18 平台实测校正）

型号结构 `<TL>-IPC<数字><系列字母>[P]-<焦距>`，四段各有含义：

| 段位 | 含义 | 认法 |
|---|---|---|
| `IPC` 后 3 位数字 | 像素 + 形态 | 首位 **4=半球 / 5=筒机**；次位 **3=300万 / 4=400万**（`445`=400万半球、`544`=400万筒机、`435`=300万半球） |
| 数字后的字母 | **系列** | `F` / `G` / `E`（`TL-IPC445`**`F`**`-W4`） |
| 系列字母后的 `P` | **PoE 供电能力** | **有 `P` = DC/PoE 双供电；无 `P` = 仅 DC 供电**（不带 P 的接不了 PoE 交换机） |
| `-` 之后 | 焦距 / 是否双光全彩 | 带 `W`（`-W2.8/-W4/-W6`）= **双光全彩**；不带 `W`（`-4/-6`）= **红外** |

⚠️ **`P` 是 PoE，不是"系列标记"**（2026-10-18 平台 16 组对照实测，F/G/E 三个系列全部一致）：

| 型号 | 平台名称 | 供电（`desc` / `spec` 实证） | 平台列表价 |
|---|---|---|---|
| `TL-IPC445F-W4` | 400万半球型音频双光全彩网络摄像机 | **仅 DC**（desc：「支持DC供电」） | 285 |
| `TL-IPC445FP-W4` | 400万**PoE**半球型音频双光全彩网络摄像机 | **DC/PoE 双供电**（desc：「支持DC/PoE双供电」） | 299 |
| `TL-IPC544F-W4` | 400万筒型音频双光全彩网络摄像机 | 仅 DC（规格有「电源接口：5.5mm DC 圆口」） | 285 |
| `TL-IPC544FP-W4` | 400万**PoE**筒型音频双光全彩网络摄像机 | **PoE/DC 双供电**（desc：「支持PoE/DC双供电」） | 299 |

差别只在**能不能用 PoE 供电**，**价差约 14 元**（平台列表价，仅量级参考，不可信、不能当报价依据）。
→ 清单写「PoE 供电 / 由交换机供电」→ 选带 `P` 的；写「独立供电 / DC / 不含 PoE」→ 选**不带 `P`** 的。

## 🎯 选型的两套标准（2026-10-13 用户亲授，动手前先判是哪一套）

用户原话：**选型大部分时候就是「按参数选产品」**；真正的难点是
**① 同参数多款都能满足时怎么定；② TP 某些参数没法完全符合时怎么办**。按场景分两套标准。

### 标准一：只要「能用」的项目（自用 / 内部 / 非投标）

> 原话：**「只需要满足使用要求，拿这个就能用就行，一般接入端口满足就行，参数尽量满足，规格相近就行。」**

- 底线只有一条：**接入端口满足**（端口类型 / 数量 / 速率对得上）。
- 其余参数**尽量满足、规格相近即可**，不必逐项对齐甲方原文。
- 不标红不标橙、不出响应表；给「推荐型号 + 为什么选它 + 数量」就能交。
- 可以选**水星（最便宜档）**或**上一代在产型号**，只要够用。

### 标准二：要投标的项目（硬性）

> 原话：**「不需要完全满足一些软件需求，但硬件要满足，比如端口数量这些，就是能简单看出来
> 或者去官网能看出来不满足的，拿去投标就会被质疑……这种时候就是尽量满足明显的实质性参数。」**

判据是**「会不会被抓」** —— 甲方 / 评委**能不能简单看出来，或去官网一查就露**：

| 情况 | 处理 |
|---|---|
| **实质性硬件参数明显不满足**（端口数量/类型/速率、PoE 端口数、带机量、盘位数、光口数……一眼能看出或官网可查） | **标红**，逐行列给用户 |
| **官网看不出来满不满足的参数**（软件功能、内部算法、未公开指标、无公开资料的项） | **标橙**，并**问用户怎么处理**，不自行放过 |
| **交换容量 / 包转发率**官网值低于招标 | **标红**，但**不换型号** —— 端口满足即为实质性响应（见下「哪些硬件参数算实质性」） |
| **其他可核硬件项**（MAC 表 / 设备高度 / 带机量 / 盘位数等）官网值低于招标 | **标红**，逐行列给用户；只要端口不受影响，**不因单一容量/物理规格换型号**，TP 全系都不满足时按偏差处理 |
| 纯软件需求、不点名硬件 | 不必逐条满足，**不标色** |

- 「能简单看出来」是核心判据：端口数量这类**写进清单、官网规格一查就有**的项，
  不满足被质疑风险最高，**必须显式标红**。
- **标橙项绝不自行判断** —— 这正是"去问用户"的触发条件。
- 标色写在**参数列（响应参数所在列）**：红 `FFFF0000`、橙 `FFED7D31`；
  用 XML 直改的富文本写法，橙同理把 `build_red_bold_cell()` 里的
  `<color rgb="FFFF0000"/>` 换成 `<color rgb="FFED7D31"/>`。
- 红/橙是**交付时必须逐行讲清**的风险清单，不是装饰。

#### ⚠️ 哪些硬件参数**算**实质性、哪些**不算**（2026-10-16 用户口径修正）

用户原话：**「交换机其实只要端口够了，交换容量和包转发率可以不用管……但是如果官网显示的不满足
招标文件要求，可以标红，但是不作为选型依据。」**

| 参数类别 | 是否作为**选型门槛** | 不满足时怎么办 |
|---|---|---|
| **端口数量 / 类型 / 速率**（含光口数、PoE 口数、万兆口数） | ✅ **是** —— 这是"实质性响应"的核心 | **必须换型号**，直到端口逐项对上 |
| **交换容量 / 包转发率** | ❌ **否** —— 仅此两项只作偏差提示 | **照样标红**（供评标答疑），但**不因此换型号** |
| 带机量 / 盘位数 / 无线速率 / PoE 功率 / MAC 表 / 设备高度 | ✅ 是（属可核的硬件能力） | 换型号；若 TP 全系都不满足（如高度 ≤5U、MAC ≥128K），标红并在报告里注明 |

> **理由**：端口是"能不能用"的问题；**交换容量与包转发率**这两项是"指标好不好看"的问题。
> TP 全系框式的这两项都对不上「≥256Tbps / ≥57600Mpps」那种抄自高端机型（如华为 S12700 系列）的数字，
> 按这两项卡会一路卡到**无货可选**。
> ⚠️ 豁免**仅限这两项**，其余硬件指标照常核、不满足照常换型号或标红。
> **标红 ≠ 淘汰** —— 标红是"如实告知风险"，选型仍以端口为准。
> 标红内容里要写清"此项为偏差提示、不作为选型依据"，避免用户误读成"这型号不能用"。

### 选型号的通用次序（两套标准都适用）

1. 先**按参数反查候选**（端口/速率/PoE/带机量等）—— 走 dealer 平台或本地备份
2. **过 CRM `lifeCycle` 滤掉停产**（必做，见下节）
3. 看归属档次：渠道 → 域联（渠道里的高控价线）→ 行业（价格保护更好）；**水星最便宜**
   （各档的**字段判据**见上文「三档怎么在数据里认出来」表）
4. **同参数多款都能满足 → 默认选最便宜的**（用户 2026-10-13 明确）
5. 商务口径（折扣）不在这步，**每次问用户**

> 一句话：**标准一是「够用就行」，标准二是「不能被抓」。**

## 品牌词中性化（重要，投标合规）

### 判定标准（2026-09-24 用户明确）

> **只要捕捉到品牌倾向，保留原意思替换，读得还通顺就 OK。**

三条同时满足才算做完：
1. **捕捉到品牌倾向** —— 自家品牌/自有平台名、以及竞品品牌名，都算。
2. **保留原意思** —— 换完不能把技术含义换掉。替换词必须是**语义等价**的行业通用表述，

| 收尾项 | 处理 | 例 |
|---|---|---|
| 孤立「的」 | 品牌词被删空会留下「的」 | `支持TP-LINK的AP` → `支持AP` |
| 重复「主流品牌」 | 多个竞品名相邻会替换出重复 | `兼容海康、大华、宇视等主流品牌设备` → `兼容主流品牌设备`（连「等主流品牌」也一起收） |

| 空标点/连续标点 | 替换后产生的脏标点 | `、` `，` 连续 → 合一；空括号删掉 |

> ⚠️ **反向误伤红线**：中性词**不要**再改成另一个中性词。
> 曾错写 `('商用云平台','商用网络云平台')` —— 但「商用云平台」本身已合规，
> 且它与上一条 `TP-LINK商用云平台→商用云平台` 的产物撞车，会把已正确的文本二次改写、语义漂移。
> **判据：如果一个词本身不含品牌指向性，就绝不放进 RULES。**

> ⚠️ **不能清行尾的「；」「。」**：控标参数是分条写的，分号/句号是**正常断句标点**。
> 曾把行尾清理写成 `[、,，;；]\s*$`，结果 `1、检测更稳定；` → `1、检测更稳定`，
> 分条结构被破坏、读起来断句感丢失。**行尾只清「、」「,」**。

> **多个竞品名相邻会自动去重**：见上表「重复主流品牌」行。

> **Word 文件另存的坑**：如果参数是从 Word 复制出来的，可能带全角空格、软回车（`\v`）、
> 零宽字符（`\u200b`）。`sanitize_text` 只处理半角空格，遇到这类字符要先用

## 价格取整规则（对外报价）

- **算出来的折后价**：不留小数；有小数则**向上取整**到个位为 **0 / 2 / 5**。
  - 例：212.85 → 215；331.10 → 332；137.5 → 140；**169.85 → 170**（个位 9 进位）
  - 本身已是整数则**保持原值**（例：12960 保持；7344 保持；3784 保持）
  - 个位或十位恰好已是 0/2/5 的整数（如 1680、1326）**不动**，不要凑成 1685
- **直接取标准价（面价）的型号**：**原样保留**（面价本身可能带 .5，如 137.5 / 142.5 / 221.5 / 0.9）
- **不对外展示折扣明细**：产出文件里不要写业务折扣率、标准价对照等，
  价格列标题用中性词（「含税单价」），**不要带"折扣"字样**。
- 实现见 `clean_price(v, rounded_up)`：`rounded_up=True` 用于**算出来的折后价**；
  `rounded_up=False` 用于**面价**（原样返回，只做数值化）。

### ⚠️ 用户 2026-09-23 明确「取整数」——默认就取整，不必再问

原话就是「取整数」。**以后这类清单的单价默认一律不留小数**，向上取整到个位 0/2/5，
不用每单确认（除非用户当次明说"保留原值"）。实测取整对照：

| 原值 | 取整后 |
|---|---|
| 331.1 | **332** |
| 169.85 | **170** |
| 795.6 | **800** |
| 1298.8 | **1300** |
| 5810.6 | **5812** |

**⚠️ 一个未定论的歧义点**：`5810.6` —— 本技能算 **5812**（先 `ceil` 到 5811，
再补到**向上最近**的 0/2/5 即 2）。另一种理解是先抹成整数再补到 **5 的倍数** = 5815。
两者差 3 元，出现在个位是 1/3/4/6~9 的小数上。**下次遇到这类值先跟用户确认走哪种**，
别默认一种就写下去。

## 「片区折扣 + 面价」口径（2026-09-30 智慧医院项目询价单，用户原话）

原话：**「片区折扣和面价」**。这是**最省事的一种口径表述**——直接对应技能里的
「渠道产品 vs 项目产品」两分法，不用再问：

| 类别 | 判据 | 取价 |
|---|---|---|
| **项目机型 / 行业产品** | `businessDiscount` 有值 | `标准价 × 片区折扣率`（0.45→0.43、0.43→0.40、**0.39→0.34**、0.32→0.27），算完向上取整到 0/2/5 |
| **渠道产品** | `businessDiscount` 为空 | **面价原样**，不打折 |

可直接用的 `--rate-spec`：

```json
{"mode":"by_discount_table","field":"seriesValue","values":["项目机型"],
 "table":{"0.45":0.43,"0.43":0.40,"0.39":0.34,"0.32":0.27}}
```

（脚本里就是 `BIZDISC_TO_PQ` 那张表。）

### ⚠️ 同日不同单，口径可能不一样 —— 别互相套用

2026-09-30 同一天两单：

| 单 | 用户口径 | 0.39 档最终使用率 |
|---|---|---|
| `项目清单0930`（防火墙单） | 「项目机换成**总部**折扣上三个点」 | 0.32+3点 = **0.35** |
| `智慧医院项目询价清单`（本单） | 「**片区**折扣和面价」 | **0.34** |

**同一个"0.39"档，两单差 0.01**。所以「同一天/同一客户/上次是这么算的」都不构成沿用理由，
**每单照着用户当次原话取档**。

### 面价带小数时怎么处理（本单遇到，悬而未决要问）

渠道件面价本身可能带 `.5`（本单 `TL-XAP3006GC-PoE/DC易展版` = **306.5**）。
技能脚本默认 `clean_price(..., rounded_up=False)` → **面价原样保留 306.5**。
但用户级 `MEMORY.md` 里另有「用户说过『取整数』→ 一律不留小数」的旧指示，**两条会打架**。

**处置原则：保留面价原值，并在交付回复里单独点出这一行**（数量大时给两种算法的影响金额，
例如本单 186 个 × 3.5 元 = 651 元），让用户一句话定夺。**不要默默改成 310**。

## 「总部折扣 + 3 个点」口径（2026-09-30 配单0930 防火墙单，用户原话）

原话：**「项目机换成总部折扣上三个点」**。换算：

| `businessDiscount` | 总部折扣率 | +3 点后使用率 |
|---|---|---|
| 0.45 | 0.40 | **0.43** |
| 0.43 | 0.40 | **0.43** |
| 0.39 | 0.32 | **0.35** |
| 0.32 | 0.25 | **0.28** |

- **渠道件（`businessDiscount` 为空）取面价，本次不动** —— 用户说「项目机换成…」只点名项目机型。
- 算完照常向上取整到个位 0/2/5。

### ⚠️ 用户口中的「点」不等于 0.01，必须用他给的例子反算

同一句话里用户先写「上两个点（**0.25 就是 0.28**）」，随即自己更正为「说错了，**总部折扣上三个点**」。
即 **1 个点 = 0.01，但 0.25→0.28 是 3 个点**。
**教训：用户给「上 N 个点」时，若他同时给了具体档位对照（如「0.25 就是 0.28」），
一律以例子反算系数，不要按字面 N/100 直接写公式。** 早一步问清，比按字面算错整表再返工划算。

### ⚠️ 「单价不能超过定额价」——清单有「定额价」列时的硬约束

本单表头 `A=序号 B=编码 C=名称 D=规格型号 E=所报产品技术参数 F=单位 G=数量
H=定额价 I=除税市场价 J=含税市场价 K=税率(%) L=单价 M=备注` —— **单价在 L 列**。

用户要求：**算出的单价 ≤ H 列定额价，越界必须逐行列给他，不要自行压价**。
（压到定额价常低于成本，如本单行36 高密度AP 定额只有 360 而面价 1850，压了就亏。
越界只能上报由他决策。）本单越界 5 行：36 / 37 / 43 / 45 / 47。

## 「加 8-9 个点」口径（2026-09-24 抚州S2地块，用户原话）

原话：**「价格是项目机总部折扣基础上加 8-9 个点凑整作为利润，渠道机标准价格加 8-9 个点凑整作为利润」**。

| 类别 | 算法 |
|---|---|
| **项目机**（`businessDiscount` 有值） | `面价 × 总部折扣率 → ×(1+加点) → 向上凑整` |
| **渠道机**（`businessDiscount` 为空） | `面价 → ×(1+加点) → 向上凑整` |

- 加点取什么基数：**加在折后价上**（用户 2026-09-24 明确确认）。8 个点 = ×1.08，9 个点 = ×1.09。
- 总部换算沿用 `BIZDISC_TO_HQ`：`0.45/0.43→0.40`、`0.39→0.32`、`0.32→0.25`。
- 凑整：向上到个位 0/2/5（同 `round_up_025`）。
- 实例：项目机 `TL-AH400` 面价 1320 × 0.32 = 422.4 × 1.09 = 460.4 → **462**。

### 📌 渠道加点 / 行业底折「分产品类型双口径」（2026-09-28 售楼处办公区单）

用户原话：**「渠道产品面价加 9 个点，行业产品业务底折，取整」**。

| 类别 | 判据 | 算法 |
|---|---|---|
| **渠道产品** | `businessDiscount` 为空 | `面价 × (1 + 加点)` → 向上取整 0/2/5 |
| **行业产品** | `businessDiscount` 有值 | `面价 × businessDiscount` → 向上取整 0/2/5 |

- 与上面「加 8-9 个点」的差别：**行业产品不加点**，直接给业务底折（底价口径）。
- 实测该单：13 个渠道件（域联 AP/交换机、布线件、监控件、门禁件）走 ×1.09；
  5 个 `项目机型`（`TL-NS620-8GPE1G1F` / `TL-NS620-16GP2F` / `TL-NS620-24G2F` /
  `TL-NS650-24G4F` / `TL-NVR8021-32S`，bd 全 0.39）走 ×0.39。
- **小件跳档必须提示**：面价很低的配件（面板 7、按钮 8、支架 15）经 ×1.09 再向上取整到 0/2/5
  会跳到 10 / 10 / 20，涨幅 25%~43%。算完要在回复里点出来，问用户是否改成"只抹小数"。

### 📌 「控标库查不到就不改」= 关掉官网兜底，且常是覆盖式替换（2026-09-28）

用户说 **「参数换成控标参数，有就换控标参数，控标库里查不到，就不改了」** 时：
1. **不要**走官网抓「产品特性」兜底 —— 没命中就**原样保留**原参数，一个字都不动。
2. 这是**覆盖式**替换（不是技能默认的"只填空"），F 列原有内容要整格换掉。
   含 `&nbsp;`、软回车一类的脏字符借这次替换顺手清掉。
3. 用户点名「保留备注和产品图片」时 = 只改参数列 + 价格列；K 列备注、J 列图片
   （含浮动 drawing）一律不碰。

### ⚠️ 用户特批型号：可以"按未涨价的新标准价"算

用户会在涨价前给一个**比 CRM 现值更高的标准价**，要求按它算。原话：
「TL-AS7230 标准价格你查询的是 632，但是你按 700 的标准价格算，马上要涨价了」。
→ 实现上就是**覆盖 CRM 的 price 字段**再走同一套公式。这类指示要**逐字照做**，
不要去用 CRM 现值"纠正"用户。

### ⚠️ 数量后缀可以是小数：`*0.5` = 按一半价格

早期实现只认 `*N`（整数）。实测清单里有 `TL-SA3045*0.5`（摆闸单机芯只要半副摆臂），
必须支持 **`*0.5` → 单价 × 0.5 后计入加总**。token 正则要用 `[0-9]*\.?[0-9]+`。

### 🚨 同一张表里可能存在「两套报价口径」，别去"统一"它

实测（2026-09-24 抚州S2地块）：同一清单里用户**已填**的网络+监控那批价，
和「总部折后加 9 个点」**对不上**——反推是别的算法：

| 行 | 型号 | 面价 | bd | 总部折后 | 用户已填 | 已填 ÷ 折后 |
|---|---|---|---|---|---|---|
| 61 | TL-NGP650-S2-4G | 900 | 0.39 | 290 | **356** | 1.23 |
| 63 | TL-NXAP3000-GP2 | 1470 | 0.45 | 590 | **1630** | 2.76 |
| 49 | TL-NR4914-S | 27500 | 0.39 | 8800 | **12350** | 1.40 |
| 81 | TL-NAIPC6467-W23 | 3080 | 0.45 | 1232 | **1430** | 1.16 |

用户明确指示：**「填过的网络和监控不要改，报价方式不一样」**。

**规则**：
1. **只要能填的格子，已填的一律不动**——不管机器算出来差多少。
2. 发现已填值与本次口径对不上时，**不要试图"修正"整表的算法**，也不要在回复里
   指责用户填错。正确做法：**只填空格**，并在最终回复里**如实提示**这批已填行与本次
   口径不同（供用户知情），但不改。
3. 若空白格恰好落在"已填口径"的同一类别里（如网络/监控也有空格），**先停下来问**
   该用哪套口径，别默认套本次新口径。

### 表结构各异的坑（本单实例，列位与默认 I/J/K 完全不同）

`D=品牌 E=型号 F=参数 G=项目特征 H=单位 I=工程量 J=综合单价 K=综合合价 L=备注 M=报价说明`。
→ **开工第一件事永远是 dump 表头确认列位**，本单参数在 **F**、价格在 **J**。
只服务 TP-LINK 品牌时，按 `D 列 == 'TP-LINK'` 过滤，其它品牌行（东方之光/联塑/通纳/
佳比/科华…）的型号列留着不动、参数价格都不填。

### 型号名里带 `&` 与换行的组合写法

- `TL-E201固定端&TL-E201轿厢端`：`&` 在 CRM 里是**真型号名的一部分**
  （CRM 真名 `TL-E201固定端&TL-E201轿厢端套装`）。`parse_combo` 的 `TL-` token 正则
  会把 `TL-E201固定端` 截断，需要给这类型号建**人工映射表**兜底。
- 型号单元格里用**换行**并列多个型号（行52/54/68/70）是常态，`parse_combo` 能处理，
  但**换行也会让 `main_model` 拼成 `TL-NS7606ETL-MPU600E`** 这种粘连串——
  查控标库前应先按 `[\n+/]` 切分取第一个 `TL-` token。

## 行为约定（务必遵守）

- **交付文件按「版本 + 时间」另存，不覆盖旧版**（2026-10-16 用户明确要求）：
  命名 `<项目名>_v{N}_{YYYYMMDD-HHMM}.html` / `<项目名>_v{N}.xlsx`，脚本自动扫描目录取 `max(N)+1`。
  用户会拿不同版本对照，覆盖等于把历史弄丢。

0. **动手前先判「选型标准」**：标准一（够用就行）还是标准二（投标，不能被抓）——
   决定要不要标红/标橙、要不要逐项对齐参数。详见「选型的两套标准」。
   标准二下：**明显不满足的实质性硬件参数标红**、**官网看不出满足与否的标橙并问用户**。
1. **价格折扣口径必须先问用户**，不预设、不沿用上次。详见上文「折扣口径」章节。
   取价一律走 `price_cache.py get`（**查到即落盘备份**，CRM 不可达自动读备份）——
   备份解决的是"查不到"，**不改变「折扣口径每次都要问」**。
2. **跑之前必须先 dump 表头确认列位**。清单的列位几乎每次都不一样：
   - 常见：型号 D、参数 G、单位 H、数量 I，价格列根本不存在要新建；
   - **不要套用默认的 I/J/K**！默认列位只适用于一种特定模板。
   - 脚本有「列位自检」：型号列里认不出型号（全是纯数字等）会**在写文件前中止**并退出码 2。
3. **只填空单元格**。型号列/参数列/价格列里已有内容的一律不动——用户手工填过的价往往是议价结果，
   机器算的价跟它不一致是正常的，**不要覆盖**。
4. **跳过备注行**。型号列里写的是「没有防爆球机」「没有65寸」「相关产品已停产」这类备注时，直接跳过。
5. **套装组合拆开处理**。型号形如 `TL-A+TL-B`、`TL-A/TL-B`、`TL-C*3` 时，拆出全部配件查库/查价；
   **参数按主型号（第一个）填，价格按全部配件加总**。详见上文「组合型号」章节。
6. **算出来的价跟用户填的不一致时，不要改用户的**。差异通常来自：用户加了利润点、
   A/B 成对按 2 个计价、按张/按米计价、或议价。必要时在回复里列出来提醒。
7. **产出后建议做核对页**：生成一个 HTML 对照表（行号 / 项目名称 / 型号 / 参数 / 单价 / 来源标记），
   绿色=本次新填、灰色=原有未改，方便用户逐行过一遍。
8. **核价模式**（用户说「核对一下价格」时）：只核对**型号非空且单价 > 0** 的行，逐行 dump 表头列位后再比。
   下列行**不参与比价**，也不要在报告里算差异：
   - **型号列空白**的整机/外购件（如「管理服务器」只写 CPU/内存/显示器配置、标价 2680）——不是普联物料，套不了折扣；
   - **单价 0** 的软件/授权行（型号常写 `TUMS车辆管理拓展应用授权`、`已含`，备注「已和综合管理平台整合在一起」）——
     这是「已并入平台/赠送」的写法，不是漏填；
   - 甲方给定、不报价的行（如「橡胶减速带」只填数量）。
   报告里最好单列一句「本次未核对的行 + 原因」，避免用户以为漏了。
   另外：核价前**先问折扣口径**（走总部还是片区、哪几个点），核完的改动**只改单价列**，
   总价/合计是 `=G*H` 公式会自动重算，不要手工改。

### ⚠️ 文件安全（血泪教训）

- **交付后文件会被"预览"锁住（2026-10-16 实测）**：把 xlsx 交给用户预览（present_files 等）之后，
  该文件常被编辑器占用，再 `openpyxl.save()` 会报 `PermissionError: [Errno 13] Permission denied`
  （**追加写也会报同样的错**）。**处置：别死磕覆盖，直接另存新版本文件名**（`..._v2.xlsx`）并在回复里说明；
  要就地覆盖，只能先让用户关掉预览。

- **🚨【最严重】openpyxl 存盘会彻底删掉表格里的所有图片！** 2026-09-23 实测：
  湖北农发清单原件含 **28 张产品图**（`xl/media/*.jpeg`）+ `xl/drawings/drawing1.xml`，
  用 `openpyxl.load_workbook()` → 改单元格 → `wb.save()` 之后，**`xl/media` 整个目录消失、
  drawing 全没了**，产品图片列（J 列）变成空白。用户当场发现："把产品图片弄没了"。
  - **根因**：openpyxl 不做无损 round-trip，它只认识自己加载过的图片对象；
    直接 load/save 会把原文件里的 drawing + media 全部丢弃。**这是静默的，save 不报错。**
  - **铁律：只要清单里有图片（先查 `xl/media/`），就不要用 openpyxl 存盘。**
  - **正确做法 —— 直改 XML**：把 xlsx 当 zip 打开，只重写 `xl/worksheets/sheet1.xml`
    里目标单元格的 `<c>` 节点，**其余条目（含 media/drawings/styles）原样 copy 回去**。
    参考实现见下方「XML 直改法」。
  - **开工前必查**：`zipfile.ZipFile(路径).namelist()` 里数一下 `xl/media/` 有几个文件。
    有图 → 走 XML 直改；没图 → 才可以用 openpyxl。

##### 🚨 【2026-09-30 修正】「没有图片就可以用 openpyxl」是**错的** —— 一律走 XML 直改

智慧医院单实测（无任何图片的清单）：openpyxl load→save 之后 —

| 部件 | 原件 | openpyxl 产出 | 后果 |
|---|---|---|---|
| `xl/printerSettings/*.bin` | **23** | **0** | **打印页面设置全丢**（纸张/缩放/边距/打印区域回默认）。投标清单要打印盖章，这是实打实的功能损失 |
| `xl/calcChain.xml` | 1 | 0 | 公式链丢失（可重建，影响小） |
| `numFmts / borders / cellXfs` | 13 / 19 / **687** | 12 / 26 / **1060** | 丢 1 个自定义数字格式；样式表被重写膨胀 53%，**21 张没碰过的表格式也可能被改** |
| `xl/styles.xml` 大小 | 153 KB | 208 KB | — |

也就是说 openpyxl 会**重写整个样式表**，不是"只改我碰的格子"。

**结论（写死）：不管有没有图片，改单价/参数这类"就地填数"的活，一律用 XML 直改。**
openpyxl 只用来 **只读**（算值 / 列位自检 / 校验产出）。

**XML 直改的实施要点（本次跑通的做法）**：

1. **sheet 名 → 文件名映射**：`xl/workbook.xml` 里 `<sheet name="3.网络" r:id="rIdN">`，
   再用 `xl/_rels/workbook.xml.rels` 把 `rIdN` 映到 `worksheets/sheetN.xml`。
   ⚠️ **sheet 名顺序 ≠ 文件名序号**（本单 `3.网络`→`sheet4.xml`、`5.数据中心`→`sheet6.xml`）。
2. **加新样式**：在 `xl/styles.xml` 的 `</cellXfs>` 前追加 xf，`count` +1，
   单元格用 `s="新索引"`。需要两种新格式时一次追加两条，记好各自索引。
3. 🚨 **构造 xf 必须用属性字典重建，绝不能字符串替换拼接**。
   踩坑实录：想给 xf 加 `applyNumberFormat`，写了 `xf.replace('/>', ' applyNumberFormat="1"/>')`
   —— `str.replace` 是**全部替换**，把内部 `<alignment .../>` 的 `/>` 也改了，
   产出的 XML **缺 `</xf>` 收尾**，`openpyxl.load_workbook()` 直接抛
   `ParseError: duplicate attribute`。正确做法见本次 `make_xf()`：解析原 xf 的属性
   → 字典覆盖 → 按固定属性顺序重建。
4. **写回后必须逐个 XML 做 `ET.fromstring` 校验**，坏 XML 当场就能抓到。
5. **产出后必须验证"只该变的变了"**：
   逐 sheet 比对原件 vs 产出的字节，本单应为「只有 2 张目标表变化，其余 21 张逐字节相同」；
   条目数、`printerSettings` 数、`_rels` 数三者的前后值必须一致。
6. 记得在 `xl/workbook.xml` 加 `<calcPr calcId="191029" fullCalcOnLoad="1"/>`，
   否则用不重算的查看器打开，公式列（金额）会显示空白/0。
  - **产出后必查**：对比原件与产出的条目数、media 数、drawing 引用链
    （`sheet1.xml` 含 `<drawing r:id>` → `sheet1.xml.rels` → `drawing1.xml` →
    `drawing1.xml.rels` → `xl/media/*`）。四条都对上才算没丢图。
- **优先用 `--out` 另存新文件**，不要就地写回原清单 —— 原清单是用户的资产。
- 就地写回时脚本的备份名**带时间戳**（`xxx.xlsx.20260920-104812.bak`）。
  早期用固定 `.bak` 名，连续跑两次第二次就把干净备份覆盖了，导致无法还原。
- **写文件前必须通过列位自检**。实测踩过：默认 I/J/K 跑错列位，
  把参数/价格写进了 I 列，把原有的单位数据搅乱，只能靠备份还原。
- 若发现写错了列，**立刻从备份还原**，不要试图手工修补。

### XML 直改法（有图片时必须用这个）

```python
import zipfile, re

def col_ord(letters):            # 'J' -> 10
    n = 0
    for ch in letters: n = n*26 + (ord(ch)-64)
    return n

def build_text_cell(ref, style, text):
    """普通文本格（inlineStr，保留换行）"""
    esc = text.replace('&','&amp;').replace('<','&lt;').replace('>','&gt;')
    return ('<c r="%s" s="%d" t="inlineStr"><is><t xml:space="preserve">%s</t></is></c>'
            % (ref, style, esc))

def build_red_bold_cell(ref, style, text):
    """红色加粗备注（富文本 runs）"""
    esc = text.replace('&','&amp;').replace('<','&lt;').replace('>','&gt;')
    rpr = '<rPr><rFont val="微软雅黑"/><b/><color rgb="FFFF0000"/></rPr>'
    return ('<c r="%s" s="%d" t="inlineStr"><is><r>%s<t xml:space="preserve">%s</t></r></is></c>'
            % (ref, style, rpr, esc))

def cell_style(sheet_xml, ref):
    """沿用原格样式索引，避免格式跑掉"""
    m = re.search(r'<c r="%s"([^>]*?)(?:/>|>)' % re.escape(ref), sheet_xml)
    if m:
        sm = re.search(r's="(\d+)"', m.group(1))
        if sm: return int(sm.group(1))
    return 0

def set_cell(sheet_xml, ref, new_cell_xml):
    """就地替换已存在的格；没有则按列序插入该行"""
    pat = r'<c r="%s"(?:[^>]*?)(?:/>|>.*?</c>)' % re.escape(ref)
    if re.search(pat, sheet_xml, re.S):
        return re.sub(pat, new_cell_xml, sheet_xml, count=1, flags=re.S)
    letters, rownum = re.match(r'([A-Z]+)(\d+)', ref).groups()
    rm = re.search(r'(<row r="%s"[^>]*>)(.*?)(</row>)' % rownum, sheet_xml, re.S)
    if not rm: return sheet_xml
    body, tgt = rm.group(2), col_ord(letters)
    for cm in re.finditer(r'<c r="([A-Z]+)\d+"', body):
        if col_ord(cm.group(1)) > tgt:
            body = body[:cm.start()] + new_cell_xml + body[cm.start():]
            break
    else:
        body += new_cell_xml
    return sheet_xml[:rm.start(2)] + body + sheet_xml[rm.end(2):]

# ---- 主流程：只重写 sheet1.xml，其余条目原样回写（图片得以保留）
z = zipfile.ZipFile(SRC)
sheet = z.read('xl/worksheets/sheet1.xml').decode('utf-8')
sheet = set_cell(sheet, 'F7', build_text_cell('F7', cell_style(sheet,'F7'), 参数文本))
sheet = set_cell(sheet, 'K7', build_red_bold_cell('K7', cell_style(sheet,'K7'), 备注))

zout = zipfile.ZipFile(OUT, 'w', zipfile.ZIP_DEFLATED)
for item in z.infolist():
    data = z.read(item.filename)
    if item.filename == 'xl/worksheets/sheet1.xml':
        data = sheet.encode('utf-8')
    zout.writestr(item, data)          # ← media/*.jpeg 原样写回
zout.close()
```

**要点**：
1. 数值格写成 `<c r="H7" s="92"><v>332</v></c>`（不带 `t=`，默认就是数值）；
   公式格写成 `<c r="I7" s="93"><f>G7*H7</f></c>`。
2. **样式索引 `s=` 一定要沿用原格**（`cell_style` 兜底取 0 会让边框/字体全丢）。
3. 富文本写 `inlineStr` + `<r><rPr>…</rPr><t>`，不要写 `sharedStrings.xml`
   （改共享字符串要同步 `count`/`uniqueCount`，容易写错）。
4. 想强制 Excel 重算公式，把 `xl/workbook.xml` 里换成
   `<calcPr calcId="191029" fullCalcOnLoad="1"/>`。
5. **openpyxl 只用来「读」和「验证」**，不要用来「存」带图的表。
   注意 openpyxl 读到 `ws._images == 0` 是**正常现象**（它不解析原生 drawing），
   不代表图丢了 —— **判断图有没有丢要看 zip 里的 `xl/media/` 条目数和 drawing 引用链**，
   别被 openpyxl 骗了。
6. 校验图片链路的四步：`sheet1.xml` 含 `<drawing r:id>` → `sheet1.xml.rels` 指向
   `drawing1.xml` → `drawing1.xml` 锚点数 == 图片数 → `drawing1.xml.rels` 映射到
   `xl/media/*`，且无未被引用的 media。实测清单 40 条目 / 28 media / 2 drawing 全部对齐。

### 1. 参数列为空 —— 脚本会**静默留空**

查不到参数的行，脚本不报错、不留痕，**参数列就是空的**。

布线件这类官网没建详情页的，选型库里的 `spec`（导体/护套/电气性能）足够拼出分条参数。

**做法**：抽查参数列首行文字与品类是否相符（跳线不该出现"开锁"、交换机不该出现"像素"）。
台账 `source` 字段写了官网 URL，可疑就点开核。

人才公寓单的「六类网线」行**单位是"米"、数量 3880**，脚本直接填了 `TL-EC6-305` 的
**整箱（305 米）价 747** —— 差 300 多倍。

**做法**：清单单位是 `米 / 根 / 对 / 卷` 时，回头看型号的销售单位，
按 `整箱价 ÷ 每箱长度` 折算再取整（本次 747÷305=2.45 → **2.5 元/米**），
并**在回复里单独点出这一行**交用户确认口径。

## 已知坑

- **别用 bash 双引号跑含反引号的 Python**（2026-10-16 踩）：`python -c "…`文件名`…"` 里，
  反引号会被 **shell 先做命令替换**，内容**静默变空且不报错**（写记忆、写配置时最容易中招）。
  改用**带引号的 heredoc**：`python << 'PYEOF' … PYEOF`（引号版不做变量 / 命令替换）。

| **用户在单元格内用富文本标红** | openpyxl 默认模式**读不到也保不住**单元格内的红色片段，就地写回会**静默丢失**。必须 `load_workbook(..., rich_text=True)` 打开并保存；写入前用 `CellRichText` 扫描确认哪些格含红色；只填目标列、别碰含红格 |
| **用户要求"备注红色加粗"** | 用 `CellRichText([TextBlock(InlineFont(rFont='微软雅黑', sz=11, b=True, color='FFFF0000'), 文本)])` 写入。**注意**：① 走 openpyxl 写富文本会替换整格内容，原来的普通文本会没了；② 写完后**再次读取必须仍用 `rich_text=True`**，否则读到的是纯字符串、看着像"格式丢了"；③ 验证时检查 `blk.font.color.rgb == 'FFFF0000'` 且 `blk.font.b == True` |
| 原文件被 WPS/Excel 占用 | `wb.save()` 抛 `PermissionError`（目录下可见 `~$文件名.xlsx` 锁文件）。**不要反复重试覆盖**（用户编辑器里有未保存缓冲，覆盖会互相打架），降级为另存 `_已填.xlsx` 并提示用户关闭后自行替换 |
| requests 访问 CRM 报 SSL 证书错误 | `$CRM_BASE` 是内网域名，证书链验证不过；`requests` 需 `verify=False`（或 `ssl.CERT_NONE` context），urllib 参考实现同样处理 |
| CRM 返回的 `businessDiscount` 是**字符串** `"0.45"` | 必须 `float()` 后再查折扣对照表；否则 `bd in HQ` 永远为 False，**整表会静默退化成标准价**（实测踩过，报告全表偏高） |
| 表内价 = 标准价 × **业务底折率**（0.45/0.39/0.32），不是总部折扣价 | 核价时必须判定「表内价 ÷ 标准价」是否等于 bizDisc；是则说明填的是业务底折价，按用户口径换算（常见：11520=36000×0.32 应为 9000）。这类行是净偏高的主因 |
| 折扣率出现 **0.40 / 0.35** 等对照表外取值 | 查不到就**取标准价并问用户**，不要猜。CRM 的 TUMS 授权类（`TUMS车辆管理拓展应用授权` 37500、`TUMS访客系统拓展应用授权` 等）大量是 0.40 |
| 「对」计价的成对物料（如光模块 `TL-FC311A-3`+`B-3`、`TL-PIC350-W`+`TL-PMR300`） | 按 **2 只**标准价加总核对；单位写「个」却按「对」的价填是常见错（实测：光模块单位「个」填 120，单只标准价 60，多算一倍） |
| 清单里的配件型号**少写连字符**（如 `TL-EML200LZ`）导致 CRM 精确匹配查不到 | CRM 里真实型号是 `TL-EML200-LZ`（LZ/U/L 支架后缀带横杠）。先用模糊关键字（`EML200`）拉全家族列表，再人工挑对应件；组合价按真实型号加总（实测：190+100=290） |
| 水星（MERCURY）型号在备注里 | 也在同一个 CRM 里能查到（如 `MIPC434PW-4`、`MIPC498PW-4`，标准价 95、无业务折扣），不必去外网查 |
| **同一型号 CRM 返回多条**（`TL-EC5e-305B` 6 条、`TL-SG1008D` 3 条）—— 那是**阶梯价 `ladderPrice`** 的历史档 | **只有 `valid == true` 的那一条是现行面价**（其余是 2020~2021 年的旧阶梯档，`valid=false`）。按 `valid` 过滤后通常只剩 1 条。不过滤就会误报"多条目需人工确认"。实测：`TL-EC5e-305B`→510、`TL-SG1008D`→99，与用户手填值一致 |
| **型号单元格用换行/中文逗号并列多个型号**（`TL-VPS200\nTL-LM1022，TL-SF1008D`） | `parse_combo()` 的 token 正则能正确拆出全部型号，不用预处理换行。参数取第一个，价格全加总 |
| **分项表里有的填了型号、有的整列空着**，但设备名称+规格与别的表一致 | 按**设备名称**建 `名称→型号` 映射，跨子表复用（实测 27 行：3号/宿舍/4号 三张表全是空型号，从 1号/2号 复用）。注意子表列位可能不同（机房表型号在 J 列）。规则：**只做精确同名匹配**，`setdefault` 保留首次出现；已填型号的行**一律不动**；同型号要缓存单价，保证跨表同价；用户说「接近的也拿来用」时，**先把候选行列出来问**，别自行模糊匹配 |
| **施工/土建项本来就没有型号**，复用后会留下「空型号」行 | 这些必须跳过，不是漏填：`电源线 · 立杆 · 光缆 · 防水箱 · 室外机柜 · 配件 · 开挖 · 安装调试费 · 简易落地支架 · 广告门按钮立柱 · 安全岛`（原文这些行在 1号/2号 表里同样为空，核对时不要误判为失败行） |
| **用 openpyxl 给清单加一列**（如补「参数」列） | 五个坑，缺一个就写坏文件：① **必须先 `unmerge_cells` 再 `insert_cols`**（插列会移走合并区占位格，之后 unmerge 报 `KeyError: (1, 8)`）；② **表内公式的引用范围不随列偏移**——`I18=SUM(I3:I17)` 插列后变成 `J18=SUM(I3:I17)`，会去加"单价"列，必须手工改写成 `SUM(J3:J17)`；③ **合并范围不随偏移**（`A1:J1`/`A14:H14` 要手工扩一列）；④ **跨表引用不随偏移**（`汇总!C5='3号'!I37` 要手工改成 `J37`）；⑤ **公式缓存值会被丢掉**——openpyxl 不算公式，保存后 `data_only` 读出来全是 `None`。必须补 `wb.calculation = CalcProperties(calcId=191029, fullCalcOnLoad=True)`，否则用不重算的查看器打开会看到金额列空白 |
| **型号里带 `/`，但那 `/` 是型号的一部分**（实测 `TL-XAP3006GC-PoE/DC易展版`） | 会被 `parse_combo()` 当组合拆断（`TL-XAP3006GC-PoE` + `DC易展版`），后者查不到 → 整行报错或漏件。**正确做法：查询前先拿整串查一次**，命中唯一有效记录就直接用整串；只有整串查不到才走拆分。2026-09-30 配单0930 实测 |
| **同系列多名称并存、价格不同**（`TL-AP1202GI-PoE 薄款（方）` 面价 **100**，`TL-AP1202GI-PoE 薄款（方）**易展版**` 面价 **171**） | 清单型号名少写后缀时，查到的价与用户实际想报的价**不是一回事**（静默错价，差 71%）。填完价要**回查「名称 → 价格」是否对应**：用户填的值若等于同系列另一名的价，就提示补后缀。2026-09-30 实测行37 |
| **多子表清单里只有少数子表带型号列**（2026-09-30 智慧医院单，23 张分项表） | 开工先**全文正则扫型号**（`TL-\|YLS\|NBS\|海康\|大华\|宇视\|华为`）定位真实工作量。本单 23 表里只有 `3.网络`、`5.数据中心` 两表有型号列（**F 列**，且 `A=序号 B=名称 C=规格参数 D=单位 E=数量 F=型号 G=参数 H=单价 I=金额 J=备注`），其余 21 表是甲方通用规格、**根本没有型号列** → 不填、不动。别按"表数量"估工作量，也别去覆盖 C 列的甲方原规格。 |
| **金额列看着是 0，其实是公式** | `data_only=True` 读出的 `0` 可能来自 `=H5*E5` 的**未缓存结果**。用 `data_only=False` 复核一次列位再动手；本单 I 列全是公式，只需填 H（单价），**别手工去填 I** —— 但要记得开 `fullCalcOnLoad`，否则不重算的查看器会显示 0。 |
| **用户手改文件后要求「检查一下」** | 不要重算覆盖。正确流程：① `diff` 原文件 vs 已填文件的**每一格**，定位用户改了哪些行/列；② 对**已填文件的现状**（不是原文件）逐行跑 CRM 重算，输出「现值 vs 应然」比对表；③ 只生成核对页 HTML，**不写 xlsx**。手改常发生在「超定额价」的行上——用户会换型+换参数+换价，三列一起动 |

## 附加能力：清单设备统计 + 网关 NAT 分类

工程清单常被追问一句：「这套里哪些设备要走网关做 NAT？」——用于规划出口带宽、并发会话数、
VLAN 划分与地址池。`scripts/nat_classify.py` 把全清单条目枚举出来后逐条判定：

```bash
python scripts/nat_classify.py --xlsx "清单.xlsx" --sheet "智能化专业清单（国产一档）" \
    --out-json items_nat.json --out-html nat_report.html
python scripts/nat_classify.py --selftest      # 不联网，验证判定规则
```

判定口径（四档）：

| 判定 | 含义 | 典型设备 |
|---|---|---|
| **需走网关 NAT** | 自身有 IP，且会主动发起跨网段/外网通信 | **交换机（网管型）**、摄像机、NVR、磁盘阵列（带 RJ45，如 TL-NVS7242-256）、解码器、AP、AC、无线网桥、门禁控制器、人脸一体机、梯控、道闸、车位引导控制器、IP 广播、信息发布终端、BA 网络引擎/DDC/PLC、工作站、服务器、网络打印机、UPS（网管卡） |
| **不需走网关 NAT** | 无独立 IP，或仅在同二层域内转发/受控/供电 | 光模块、光纤收发器（非网管）、配线架、线缆管槽、机柜、支架、**门禁读卡器（韦根26/34 挂控制器下）**、锁具/按钮/卡、总线传感器、报警防区模块/键盘、电子围栏、对讲射频件、智能照明总线模块、模拟音视频设备、拼接屏/液晶显示屏、软件（部署于服务器）、配电与接地材料 |
| **视选型而定** | 是否带网络口取决于型号 | 网络发卡器、带网口控制的投影机/音频处理器、报警联动模块 |
| **不适用** | 清单备注行（"没有防爆球机"/"相关产品已停产"） | 仅指型号无从填写；**做带机量核算时仍要计入**（设备需求真实存在） |

> **两条口径更正（2026-09-22，用户明确纠正，勿再犯错）**
> 1. **交换机必须算「需走网关 NAT」**。早期写成"仅做二层/三层转发，NAT 由网关承担"是错的：
>    网管型交换机自身持有管理 IP，且清单里的型号（TL-SG2210 / TL-SH5428 / YLS220 系列 /
>    TL-NS 框式）全部支持商用云平台与商云 APP 远程管理、告警上报——这些流量必须经网关出公网。
> 2. **磁盘阵列是「需走」，门禁读卡器是「不需」**。TL-NVS7242-256 带 2 个千兆 RJ45、可作存储服务器；
>    而 TL-CR100-M 读卡器是韦根 26/34 通信，挂门禁控制器下，不占 IP。

### ⚠️ 规则顺序是个坑（务必看）

规则表**从上往下匹配、先命中先返回**。实测踩过两次：

1. 摄像机规则 `摄像机|球机|枪机|半球` 排在前面，把「**球机壁装支架**」「**枪机吊装支架**」
   一并吃成了"需走 NAT"——它们是纯结构件。
   → 所以「支架 / 立杆 / 机柜 / 箱体」这几条**必须放在文件最前面**。
2. 早期的机柜规则写成裸 `机柜`，把「**机柜式IP功放**」（IP 广播功放，确实要走 NAT）误伤成"不需走"。
   → 要写成 `网络机柜|服务器机柜`，别用裸 `机柜`。

`--selftest` 里已经锁住这两个顺序陷阱（21 条断言），改规则时先跑自测。

### ⚠️ 列位必须显式传（2026-09-24 新增，实测踩到大坑）

`extract()` 的列位默认值（model_col=9/I、param_col=10/J、price_col=11/K、
name_col=3/C、unit_col=7/G、qty_col=8/H、seq_col=1/A）**只对应一种常见模板**。
实测 `0914无线网络设备清单.xlsx` 的表头是
`A=序号 B=项目名称 C=品牌 D=型号 F=参数 G=数量 H=单位 I=单价 J=小计 K=备注`，
与默认值**四列错位**（name 2≠3、model 4≠9、qty 7≠8、unit 8≠7）——
结果整表按「品牌」列当设备名判定，14 条里 13 条落到"未命中规则"，看起来像规则失效，
**其实是列读错了**。这类错误静默无报错，最容易误判成"规则不灵"。

现在 `nat_classify.py` / `capacity_check.py` 都支持 CLI 覆盖列位：

```bash
python nat_classify.py --xlsx "清单.xlsx" \
    --seq-col 1 --name-col 2 --model-col 4 --qty-col 7 --unit-col 8 --price-col 10
```

调用前**先 dump 前几行表头确认列位**。参考实现见 `tplink-helper/tools.py` 的
`detect_cols()`：按「序号 / 设备名称·材料名称·项目名称 / 型号 / 数量 / 单位 / 小计」提示词
在前 8 行里找列号，命中即用；探不到才退回默认值。

### 规则缺口修补（2026-09-24 实测清单暴露）

| 症状 | 原因 | 修正 |
|---|---|---|
| `无线控制器` 落到"未命中" | 规则写死成 `无线控制器（AC）`，清单没写括号 | 改为 `无线控制器\|无线控制设备\|^AC$\|（AC）$` |
| `上网行为管理` 落到"未命中" | 出口设备规则漏了它 | 加进 `^防火墙$…` 那条 |
| `定向天线` / `射频线缆` 落到"未命中" | 射频规则只列了"全向天线/室外天线/馈线接头" | 补 `定向天线\|天线$\|射频线缆\|馈线` |

## 附加能力：网关带机量核算（判断出口设备够不够）

被问「这台网关/路由器带机量够不够」时用 `scripts/capacity_check.py`。它把清单里
**需经网关的 IP 主机数**算出来，与出口设备的**最大带机量**（自动从控标库解析）对比。

```bash
python scripts/capacity_check.py --xlsx "清单.xlsx" --sheet "智能化专业清单（国产一档）" \
    --exit "151:TL-ER8920T" --exit "152:TL-NR4914-S" --exit TL-NR6700 \
    --info-points 1800 --out-json cap.json

# 只算网络设备（交换机 + 无线 AP + 无线控制器 AC），剔除监控/门禁/广播/BA
python scripts/capacity_check.py --xlsx "清单.xlsx" --scope net \
    --exit "150:TL-FW5900" --exit "152:TL-NR4914-S"
```

- `--exit` 可重复，格式 `行号:型号` 或 `型号`；带机量自动解析（同时打印并发数、纯 NAT 吞吐）。
- `--info-points` 工位终端数（清单未列时人工给）。**不含它只算网络设备管理面，含它才是全量。**
- `--scope all|net`：**问法决定口径，先看清用户在问什么**。
  - `all`（默认）= 全量 IP 主机（含监控、门禁、广播、BA 等业务设备）。
  - `net` = 只计网络基础设施（交换机 / AP / AC）。用户说「只算交换机、AP 和网络设备，
    不算监控门禁」时用这个。
  - ⚠️ 别擅自替用户选口径。两种口径在 0918 清单上差 2.5 倍（4001 vs 1494），
    结论甚至会**反转**（瓶颈从 152 网关变成 150 防火墙）。用户口径变了就重算，别沿用上一版。
- ⚠️ **控标库里防火墙/路由器/网关多数没有「带机量」这一项**，脚本会自动去官方规格 JSON
  兜底（路径见下），并标注来源。若两边都没有，说明要向产品线索取规格，别猜。
- ⚠️ **规格表 JSON 里 model 字段带版本号后缀**，形如 `TL-FW5900  1.0`（两个空格 + 版本）。
  按型号匹配时**必须先按空白切分**，否则裸型号永远匹配不上（这个坑踩过一次，静默返回空）。


### 核算口径（四条，缺一不可）

1. **先定统计范围**（`--scope`）：问「带机量够不够」时先确认算不算监控/门禁等业务设备。
   用户说「只算交换机和 AP」就用 `--scope net`。**范围不同结论会反转，不能沿用上一版。**
2. **交换机计入**：网管交换机是一台独立 IP 主机（见上节口径更正）。
3. **出口设备扣除**：防火墙/路由器/网关/安全网关自身是 NAT 路径上的转发设备，不"被带机"，
   脚本自动单列（限「计算机网络系统」内，避免误扣楼宇自控系统的"网关"）。
4. **备注行计入**：清单标"没有 XX 产品"的行，型号虽空但设备要装、要占 IP，不能漏。

### 判断标准

按**负载率**（需求 ÷ 额定带机量）判，比"倍数"更直观，也与工程惯例一致：

| 负载率 | 结论 |
|---|---|
| ≤ 70% | **够**，余量充裕 |
| 70% ～ 85% | **够但偏紧**，扩容即触顶 |
| 85% ～ 100% | **够但卡线**，不建议（如 NFW8300 的 99.6%） |
| > 100% | **不足** —— 找出链路里带机量最小的那台（串联架构的瓶颈） |

> 清单里同型号 ×2：**双机热备按单台带机量衡量**（备机不承载）；**负载分担才可 ×2**。
> 判不准就问用户部署方式，别默认。

### 实测案例（0918 集采清单，654 条）

**全量口径（`--scope all`）**：需经网关 IP 主机 **4001 台**（交换机 822、AP 670、摄像机 1135）；
加 1800 工位终端 = **5801 台**。串联链路上：150 防火墙 **TL-FW5900 官方带机量只有 600 台（不够）**；
151 路由器 TL-ER8920T（10000）够但**已停产**；**152 网关 TL-NR4914-S（仅 2000）也会超载**。

**网络设备口径（`--scope net`，用户 2026-09-22 指定的口径）**：只计
交换机 **822** + 无线 AP **670** + AC **2** = **1494 台**。此时结论反转：

| 行 | 型号 | 带机量 | 负载率 | 判定 |
|---|---|---|---|---|
| 150 | TL-FW5900 | 600 | 249.0% | **不足**（缺口 894）← 唯一瓶颈 |
| 151 | TL-ER8920T | 10000 | 14.9% | 够（但已停产） |
| 152 | TL-NR4914-S | 2000 | 74.7% | 够但偏紧（余量 506） |

改型：150 → **NFW8600E**（5000，负载 29.9%，片区折后 30,284，唯一"达标不卡线"的在产防火墙）；
NFW8300（1500）虽够但负载 99.6%，不建议。152 若日后扩容 → NASG6007（5000）或 NR6700（20000）。

⚠️ **口径一变，结论随时反转**：全量口径下 152 是瓶颈，net 口径下 152 够用、150 才是短板。
所以**每次都要按用户当次口径重算并说明口径**，不要沿用上一版结论。

⚠️ **NR6700 与 NR4914-S 不同类**：NR6700 是园区出口路由器（行为管理仅基础级，免费 585 应用）；
NR4914-S 是"多业务安全网关"（完整行为审计 + 一体化 DPI）。**换型前先问清 152 行的本意是
"出口路由"还是"上网行为管理"**，二者导向不同型号。

## 选防火墙/出口设备时的必查清单（2026-09-22 增补，踩过坑）

选型别只看"参数够不够"，下面四项任一漏掉都会翻车：

1. **带机量**：查官方规格 JSON（见上）。注意**档位是断层的**——
   600 / 1000 / 1500 / 5000 / 10000，**2000~4000 这一档是空的**（原本的 NFW8500=3000、
   NASG6005=3000 都已停产）。项目规模落在这个断层里时，只能往上一档跳，价格会跳 6~10 倍。
2. **在产状态**：查 CRM 的 `lifeCycle` 字段（`PRODUCTION`=在产 / `HALT`=停产）。
   已知停产：NFW8500、NFW8600、NFW7600、NASG6005、FW6600、FW6300、**ER8920T**。
   停产机型投标要慎重（供货/备件/licence 都是隐患）。**填型号前一律先查 lifeCycle。**
3. **部署模式**：同一张规格表里**路由模式与网桥模式的吞吐量级能差 6 倍**
   （FW5900：路由 19.8Gbps / 网桥 3.3Gbps；NFW6628 恰好相反）。
   技术应答前先与用户确认实际部署模式，别拿错那一列。
4. **License 是第二笔钱**：`TL-FW-LIS-ALL` 200 元（低端机型）/ `TL-FW-LIS-ALL-E` 800 元
   （**3000 元档及以上**，本批防火墙候选全适用）。
   - IPS、AV、恶意域名三库**出厂规格 = 0，不买 license 完全不能用，过期即失效**。
   - 买了多合一**不能与单库混搭**。单买五库合计 4200 元 vs 多合一 800 元 → 走多合一。
   - 报价时把 license 按**台数**计入（双机热备就是 ×2）。
   - **含授权库时的算法（用户 2026-09-30 明确纠正，以此为准）**：
     **防火墙本体先打折，再把授权价原价加上去 —— 授权不参与折扣。**
     实测 2026-09-30 配单0930：`TL-NFW6628` 34550 × 0.35（总部 0.25+3点）= 12095，
     再加 `TL-FW-LIS-ALL-E` 800 × 3 年 = 2400 → **单价 14495**；
     M 列备注写「含3年三合一库授权（IPS+AV+恶意域名库）」。
     - ⚠️ 本技能**早前记成「把授权价并入基数再打折，不要折完再加」——那是错的**，
       2026-09-30 用户当面纠正。**先折后加**，别再搞反。
     - ⚠️ **备注必须写清年限**（用户原话：「加了的话你要备注加了几年」）。
       授权按年计价，年限由用户当次指定，别自己定。
     - ⚠️ **加满年限后若超定额价 → 降级**（本单口径：3 年超了降 1 年）。

### 另一个坑：控标库参数与官方规格表数字对不上

J150 曾填「全威胁吞吐量不少于 730Mbps」，官方表上 FW5900 只有 **226/456Mbps**；
「新建连接 38400 条/s」对官方 **34,962 CPS**。规格表底部原文说明：
「括号内是 128KB 的 HTTP 容量下的参数（接近实际吞吐量），括号外是 10KB 下的参数。
**实际宣传时按括号内较高的数值**（官网就是按该数值宣传）」。
→ 对外应答请取 **128KB 档**的数字，并先与产品线确认控标库那组数字的测试版本，
否则被索要检测报告会对不上。

## 直接 import 脚本时的 API 签名（2026-09-28 踩坑，写定制脚本必看）

需要按新口径另写脚本时（技能自带的 `main()` 只支持"只填空"），常 `importlib` 加载本脚本复用函数。
**两个返回值是元组，漏接会静默出错**：

| 函数 | 真实返回 | 漏接的后果 |
|---|---|---|
| `crm_login(email, pwd)` | `(opener, resp_json)` **元组** | 把元组当 opener 用 → `crm_price` 内部 `except` 吞掉异常 → **静默返回 `[]`**，表现为"全部型号查不到价" |
| `load_kb(path)` | `(idx, kb_list)` **元组** | 遍历时 `'list' object has no attribute 'get'` |

正确写法：`op, _j = m.crm_login(em, pw)` / `idx, kb = m.load_kb(m.DEFAULT_KB)`。
取价正确姿势：`rows = m.crm_price(op, model)` → 按 `valid is True` 过滤 → 命中多条要人工裁决。
凭证仍在 `~/.workbuddy/MEMORY.md`（正则 `[\w\.\-]+@[\w\.\-]+\.\w+` 取邮箱，`密码\**\s*[：:]\s*`([^`\n]+)`` 取密码），照抄 `main()` 里的读法。

## 改价后必做：刷新公式缓存 + 开重算（2026-09-28）

清单的「总价」列常是**共享公式**（实测 `I7:I24` 为 `<f t="shared" ref="I7:I24" si="0">H7*G7</f>`，
其余行只有 `<f t="shared" si="0"/>`）。**XML 直改只改 `<v>` 缓存值不会自动重算**，
不重算的查看器（部分 WPS/看图工具）会显示旧金额。

两件都做：
1. **手工刷新每行缓存**：`<c r="I7" ...><f .../>**<v>新值</v>**</c>` —— 只替换 `<v>`，公式原样保留；
   合计格（如 `J26 = SUM(I7:I25)`）的 `<v>` 同步刷。
2. **workbook.xml 开重算**：`<calcPr calcId="191029"/>` → `<calcPr calcId="191029" fullCalcOnLoad="1"/>`。

⚠️ 顺带两个格式坑：
- **H 列 numFmt 可能是 `0.00_ `（两位小数）**，取整后的整数会显示成 `350.00`。想显示纯整数要另建 numFmt，
  但**改样式会波及共用同一样式索引的格**，默认保持原格式不动、在回复里提一句。
- **控标库的加分项标记不统一**：多数条目用 `★`，个别（如 `TL-NS650-24G4F`）用 `*`，
  且 `is_bonus: true` 就是加分项。直接填会与同表其他行不一致，可问用户是否统一成 `★`。
